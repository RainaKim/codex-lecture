# 15강 스피커 노트 — No Silent Fallback: 조용히 실패하는 코드 막기

> Part 2 · Chapter 3 · 15강 · **이론+실습** · 약 40분 · 4클립
> 슬라이드: `lec15.html` (19장). Lab 정본: `labs/lecture15/README.md` (222줄).
> 산출물: `docs/retry-stop-matrix.md` · `docs/checklists/failure-handling.md` · 두 fallback 제거 diff와 예외 경로 테스트 + 커밋 하나.
> ⚠️ **이 강의는 12강 이후 `src/`가 처음 바뀐다.** 13·14강은 `src/` 순변경이 없었다. 대신 **후보 검토 → 사람 승인 → 변경** 순서를 지킨다.
> ⚠️ **이전 Lab의 관리자 상태 `it.fails()` 테스트는 이 강의에서 그대로 둔다.** 두 catch 제거와 별개인 문제다.

## 이 노트 쓰는 법

- 인용부호 안은 **그대로 읽어도 되는 말**이다. `[…]`는 화면 조작, `⚠️`는 놓치면 뒤가 어긋나는 지점.
- 화면 지시는 **`[슬라이드 NN]`** 또는 **`[README N장 · 절 이름]`** 형식이다. 코드·문서는 `파일:줄`로 적었다.
- ⚠️ **줄 번호는 리허설(`order-ops-demo`) 기준이다.** Lab 12를 라이브로 구현하면 밀린다. **촬영 직전에 다시 찍어 적어 둔다.** 어긋나면 이름으로 찾는다.
- ⚠️ **E1 → E2 → E3는 같은 세션에서 이어 간다.** E2 프롬프트가 「현재 fallback 조사 결과」를, E2 구현·E3 프롬프트가 「방금 세션에서 승인한 오류 처리 경계」를 가리킨다. **새 Task를 열면 가리킬 대상이 사라진다.**
- **시간 표기는 노트에만 있다.** 슬라이드에도 README에도 화면에 띄우지 않는다.
- **「심화 (강사)」는 선택이다.** 시간이 남을 때나 질문이 나올 때 꺼낸다. 다 하면 5~6분 길어진다. **40분이 빠듯하니 심화는 기본적으로 건너뛴다.**
- ⚠️ **심화의 내용은 일반적인 개발 상식이다.** 이 강의를 위해 외부 문서로 근거를 확인한 것이 아니다. **「공식 문서에 이렇게 나와 있다」고 말하지 않는다.**
- 코드는 줄마다 설명하지 않는다. **무슨 값이 어디로 나가는지**만 짚는다.

## 시작 상태 (강사가 미리 확인)

- **Lab 14 종료 상태**여야 한다. 테스트가 보강돼 있고, **관리자 상태 표시 테스트 하나가 `it.fails()`로 표시**돼 있어야 한다.
- 작업 트리가 **깨끗해야** 한다. 이번에는 `src/`가 바뀌므로 **출발선이 비어 있어야** 나중에 diff를 읽을 수 있다.
- 두 fallback이 **그대로 있어야** 한다. `src/admin.ts:34~38`의 `catch { res.json([]) }`, `src/payments.ts:133~136`의 `catch (e) { console.log(e); res.json({ ok: false }); }`.
- `docs/retry-stop-matrix.md`와 `docs/checklists/failure-handling.md`가 **아직 없어야** 한다. 지난 리허설에서 남은 게 있으면 지우고 시작한다.

```bash
git status --short --branch
git log --oneline -3 -- src tests
git diff --stat -- src tests
```

⚠️ **마지막 줄이 비어 있어야 한다.** 비어 있지 않으면 **어디까지가 이번 강의의 변경인지** 구분할 수 없다. 여기서 멈추고 정리한다.

## 슬라이드 03 — Silent fallback의 유형 (1.5분)

`[슬라이드 03 — 정의 줄]`
> "정의부터 하겠습니다. **silent fallback은 예외가 발생했는데도 정상 결과처럼 보이는 값을 반환하는 코드**입니다."

`[카드 셋을 왼쪽부터]`
> "모양이 세 가지 있습니다."
> "첫째, **빈 값을 돌려주는 것.** 빈 배열 같은 거요. 받는 쪽에서는 **「데이터가 없다」와 구분이 안 됩니다.**"
> "둘째, **기본값을 돌려주는 것.** 정상 응답이랑 **모양이 똑같습니다.**"
> "셋째, **로그만 남기고 그냥 진행하는 것.** 로그에는 남는데 **호출한 쪽에는 오류가 전달되지 않습니다.**"

⚠️ **보충 줄을 꼭 읽는다. 「빈 배열은 무조건 나쁘다」로 외우면 안 된다.**
> "빈 배열이나 기본 객체가 **나쁘다는 얘기는 아닙니다.** 정말 데이터가 없어서 빈 배열을 주는 건 정상이에요.
> **예외가 났는데도** 그걸 정상 결과로 돌려줄 때만 해당됩니다."

**심화 (강사) — 방어적인 코드처럼 보여서 통과한다**
> "이런 코드가 리뷰에서 잘 통과하는 이유가 있어요. `try/catch`가 있으니까 **조심해서 짠 코드처럼 보입니다.**
> 서버가 안 죽으니까 좋은 거 아니냐고 생각하기도 쉽고요."
> "그런데 **서버가 안 죽는 것과 실패를 알 수 있는 것은 다른 얘기**입니다."

`[레드 한 줄]`

> "셋째 줄이 **diff**입니다. **catch가 어떻게 바뀌었는지**, 그리고 **승인한 것 말고 다른 게 안 들어갔는지** 봅니다."

`[README 4장의 체크박스 다섯 개를 위에서 아래로]`
> "**두 fallback이 실패를 성공 모양으로 안 바꾸나. 승인한 경계와 일치하나. 두 예외 경로와 정상 경로를 같이 검증했나. 매트릭스가 확정과 미결을 구분하나. 커밋 범위를 지켰나.**"

> "**형식 검사가 통과한 것과 이 diff는 다른 얘기**입니다. 검사기는 **파일이 있고 항목이 여섯 개인지**를 보고, 이 diff는 **승인한 대로 바뀌었는지**를 봅니다."

## 수강생 질문과 짧은 답

**"`try/catch`를 쓰면 안 되나요?"**
> "써도 됩니다. **문제는 catch 안에서 정상 값을 돌려주는 것**이에요. **잡아서 안전한 오류 응답으로 바꾸고, 원인은 서버에 남기면** 됩니다."

**"빈 배열을 돌려주면 안 되나요?"**
> "**정말로 데이터가 없을 때**는 돌려줘도 됩니다. **예외가 났는데도** 같은 값을 돌려주면, 받는 쪽이 **둘을 구분할 수 없어서** 문제예요."

**"`console.error`로 남기면 되지 않나요?"**
> "남기는 건 좋습니다. 그런데 **응답이 정상으로 나가면 호출한 쪽은 모릅니다.** **로그와 응답은 따로** 봐야 해요."

**"왜 500인가요?"** (승인 예시를 500으로 했을 때)
> "**정책이 안 정했으니까 이번에는 제가 정했습니다.** 다른 값을 승인해도 **구조는 같아요.** 중요한 건 **정한 사람이 있고 기록이 남는다**는 겁니다."

**"재시도 라이브러리를 쓰면 해결 아닌가요?"**
> "라이브러리는 **어떻게 다시 시도하는지**를 줍니다. **언제 다시 시도해도 되는지**는 정책이 정해야 해요. 결제는 특히 그렇고요."

**"Codex가 fallback 후보를 안 내놓으면요?"**
> "그래서 **고정 후보**를 준비해 뒀습니다. **제가 하나 말씀드리고 같은 세 질문으로** 판정하면 돼요."

## 자주 하는 실수 (강사가 실습 중 경계할 것)

- **기존 catch를 다른 빈 값이나 기본 성공 응답으로 바꾼다.** 값만 바뀌어도 fallback이다.
- **승인 없이 Codex가 상태 코드·본문·보존 방식을 정하게 둔다.** E2의 1단계에서 후보만 받는다.
- **내부 예외·스택·카드 정보를 외부 응답에 넣는다.** 반대로 **서버 쪽 원인 근거까지 버리는** 것도 같은 실수다.
- **정책이 보류한 재시도 횟수나 식별 방식을 사실처럼 적는다.** 자동 재시도 코드를 만드는 것도 범위 밖이다.
- **세션을 바꾼다.** 「방금 세션에서 승인한」이 가리킬 대상이 사라진다.
- **이전 Lab의 `it.fails()`를 건드린다.** 이 강의의 범위가 아니다.
- **E1에서 찾으면서 고친다.** 프롬프트의 마지막 줄이 막는 것이다.
- **정상 경로 테스트를 안 돌린다.** 고치다가 정상이 깨지는 걸 놓친다.
