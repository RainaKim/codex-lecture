> 예상 못 한 예외도 `{ ok: false }`로 바뀐다. **지금은 여기까지만 봅니다.** 정확히 어느 코드가

> 읽어라」라고 우리가 적어놨잖아요.** 4강에서 만든 그 문장이, 지금 우리 대신 탐색을 이끕니다.

## 2. Plan mode로 영향 경로 탐색 (Terra)

⚠️ **Plan mode 를 처음 쓴다. 4강 Read Only와 이어서 설명한다.**

> "이제 Plan mode를 켭니다. `Shift+Tab` 또는 `/plan`. 4강에서 Read Only 모드 얘기했죠 — 파일을
> 못 고치는 모드. Plan mode는 거기서 한 발 더 나가서 **조사하고 계획을 제안까지** 합니다.
> 지금은 후보만 찾을 거라 딱 맞아요."

계약을 친다:

```
목표: 결제 실패 상태 개선에 필요한 관련 파일 후보와 선택 이유를 찾는다
문맥: mention으로 연결한 요청 기록, 자동 로드된 root AGENTS.md, repo에서 확인되는 실제 연결
제약: 읽기만 하고 정책·수정 내용을 확정하거나 어떤 파일도 수정하지 않는다
완료 조건: 후보마다 repo 상대 경로·현재 역할·요청과 연결되는 이유·근거 위치가 있다
```

⚠️ **결과가 나와도 바로 파일에 안 옮긴다. 연결이 이어지는지 먼저 본다.**

> "후보가 나왔죠. 바로 파일에 옮기지 마세요. 먼저 **연결이 이어지는지** 봅니다 — 요청 들어오는
> 데(server), 상태·저장(store), 성공·실패 처리(payments), 결과 보는 데(admin), 그리고 기존
> 테스트까지. 오리엔테이션에서 본 그 흐름이 후보에 다 잡혔는지."

## 3. 후보를 역할로 분류 (Sol)

> "후보가 충분하면 이제 분류합니다. **이게 이 실습의 진짜 배울 점이에요.**"

계약을 친다:

```
목표: 방금 찾은 후보를 기능 수정 후보·검증 변경 후보·탐색 전용·검사 범위 근거로 분류한다
문맥: 직전 후보 표와 각 파일의 실제 import·router·test 연결
제약: 새 정책이나 구체적인 변경 방법을 만들지 않고 분류 이유를 함께 적는다
완료 조건: 모든 후보에 분류와 유지·제외 이유가 있고 누락 가능성이 보고되어 있다
```

⚠️ **관련 ≠ 수정 후보. 이 구분이 E1의 알맹이다.**

> "관련 있다고 다 고칠 파일이 아니에요. `server.ts`는 라우터를 연결하니 관련은 있지만, 우리가
> 고칠 건 아닐 수 있죠 — **탐색 전용**입니다. 테스트는 **검증 바꿀 후보**고. 결제 실패 상태를
> 실제로 바꿀 `payments`·`store`가 **기능 수정 후보**. 이걸 안 나누고 다 「고칠 파일」로 묶으면,
> 다음 단계에서 수정 범위가 뭉개집니다."

## 사람 확인 — 후보 범위 (Human Gate)

⚠️ **3강 human gate가 여기서 실물로 온다. 사람이 확인하고서야 기록으로 넘어간다.**

lab README의 「사람 확인 — 후보 범위」 다섯 항목을 같이 본다:

- 상태 타입·저장 위치가 포함됐나
- 주문 생성·결제·조회·관리자 조회가 끊김 없이 연결됐나
- 기존 테스트가 검증 변경 후보로 들어갔나
- 앱 조립 파일·검사 설정을 기능 수정 대상으로 오해 안 했나
- 정책 선택이나 수정 방법이 후보 이유에 안 섞였나

> "누락이 있으면 **어느 역할이 빠졌는지만** 알려주고 다시 찾게 합니다. 파일명을 사람이 대신
> 채워주지 마세요. 그럼 실습이 아니라 받아쓰기가 돼요."

## 4. 확인된 후보만 기록 (Default mode · Terra)

> "범위를 확인했으면 Plan mode를 끄고 Default로 돌아와서, 확인된 것만 파일에 기록합니다."

계약을 친다:

```
목표: 확인된 후보를 notes/order-status-plan.md의 ## 관련 파일 후보에 기록한다
문맥: 이 Task에서 검토하고 승인한 후보와 분류만 사용한다
제약: repo 상대 경로와 선택 이유만 쓰고 정책·수정안은 쓰지 않으며 src와 tests는 수정하지 않는다
완료 조건: 모든 경로가 존재하고 후보마다 분류와 이유가 있으며 다른 파일 변경이 없다
```

⚠️ **라인 번호를 계획 문서에 안 쓴다. 왜인지 짚는다.**

> "채팅엔 「payments.ts 87번째 줄」 이렇게 나와요. 근데 계획 문서엔 **라인 번호를 안 씁니다.**
> 코드가 한 줄만 위로 밀려도 87번이 틀려지거든요. **경로랑 역할로** 써요 — 「payments.ts, 결제
> 실패 처리」. 코드가 움직여도 뜻이 안 변하게."

## 왜 이 순서인가 (구두로)

> "탐색 결과를 바로 파일에 저장하면, 그냥 관련만 있는 파일이랑 진짜 고칠 파일이 섞여요. 먼저
> 영향 경로 확인하고 → 사람이 범위 검토하고 → 기록하면, **E2에선 이 탐색을 다시 안 하고 현재
> 동작 확인에만 집중**할 수 있습니다. 3강에서 배운 「종료 상태가 있어야 다음이 깨끗하다」랑
> 같은 얘기예요."

## 검수 + 돌아다니며 잡을 것

lab README 검증 다섯 줄이 검수 항목이다:

- 후보 세 개 이상 · 각 후보에 이유 · 네 분류로 구분 · repo 상대 경로 실재 · plan 파일 외 무변경

자주 나오는 실수 (돌아다니며 잡는다):

- **요청 단어와 파일 이름만 비교** → "import랑 라우터 연결을 따라가야죠. 이름만 비슷한 거 말고."
- **관련 파일을 다 수정 대상으로 분류** → "`server.ts`도 고칠 거예요? 관련이지 수정 후보는 아니죠."
- **채팅의 절대 경로·라인 번호를 그대로 복사** → "경로랑 역할로. 라인은 곧 틀려져요."
- **원하는 상태·응답을 벌써 구현 방법처럼 적음** → "그건 E3에서 정책 정할 때. 지금은 후보만."

> 있는지**는 아직 모르죠. 다음 단계에서 현재 동작을 표로 만듭니다."

# E2 — 현재 동작 표 만들기 (약 12~15분)

산출물은 `notes/order-status-plan.md`의 `## 현재 동작` 하나. 세 케이스를 **현재 코드로** 추적한다 —
결제 성공 · 결제 실패 · 재고 부족 주문.

⚠️ **이 단계의 핵심 한 줄: 「원하는 동작」이 아니라 「지금 코드가 하도록 적힌 동작」을 쓴다.**
fixture도 실행 결과도 안 쓴다 — 그러니 **「실행해서 관찰했다」가 아니라 「코드에서 확인했다」**로
말한다. 고치는 게 아니고, 정책을 정하는 것도 아니다. 응답·주문 상태·저장 여부·재고 변화를
**따로따로** 사실만 적는 단계다.

⚠️ **모델 tier**: 추적은 Terra, **근거 감사(사실 vs 기대 분리)는 Sol**, 기록은 Terra, 검증은 Luna.

⚠️ **시작 상태**: E1의 `## 관련 파일 후보`가 완성돼 있고 같은 Task를 계속 쓴다. 새 Task로
다시 시작한다면 `notes/order-status-plan.md`와 `notes/order-status-request.md` **두 개만** `@`로 붙인다.

## 여는 말

> "E1에서는 **어디를** 읽어야 하는지 찾았죠. 이제 그 파일들을 근거로, 이 시스템이 실제로 **어떻게
> 동작하도록 적혀 있는지** 확인합니다. 여기서 중요한 건 — **고치는 게 아니에요.** 실패 주문이
> 어떻게 '되어야' 하는지는 아직 정책 얘기고, 지금은 응답·상태·저장·재고를 **분리해서 현재
> 사실만** 적습니다."

## 1. 코드 기준 현재 동작 초안 (Plan mode · Terra)

Plan mode를 켜고(E1에서 Default로 돌아왔으면 `/plan`·`Shift+Tab`) 계약을 친다:

```
목표: 결제 성공·결제 실패·재고 부족 주문의 현재 동작을 코드 근거로 표로 정리한다
문맥: notes/order-status-plan.md의 관련 파일 후보와 현재 src·tests
제약: 원하는 정책이나 수정안을 섞지 말고 파일을 수정하지 않으며 응답·주문 상태·저장 여부·재고 변화를 구분한다
완료 조건: 세 케이스마다 시작 조건·현재 응답·처리 후 상태·주문 저장 여부·재고 변화·후속 조회·코드 근거가 있다
```

⚠️ **결과가 나와도 바로 파일에 안 쓴다.** E1처럼, 먼저 사람이 판정하고 감사시킨 뒤 기록한다.
채팅 결과에 절대 경로·라인 번호가 있어도 이 단계에선 괜찮다(사실 확인용). 파일엔 나중에 경로·역할만.

### 강사가 먼저 알고 있을 것 — 세 케이스의 코드 기준

**Codex 출력을 판정하려면 정답을 알고 있어야 한다. 이 블록이 그 기준이다. 학습자에게 먼저
보여주지 않는다.**

- **결제 성공** — 상태: 없음 → `pending` → `paid`. 재고: 주문 생성 시 차감, **결제 성공 때는
  추가 변화 없음**. 응답 `{ ok: true, order: … }`. 주문은 `orders` Map에 남음.
- **결제 실패** — 상태: 없음 → `pending` → **주문 삭제**. 응답 **HTTP 200 + `{ ok: false }`**.
  실패 시도는 `paymentAttempts`에 기록. 이후 `GET /orders/:id`는 404, 관리자 목록에도 없음.
  **주문 생성 때 깎은 재고는 복원 안 됨.**
  - ✕ 틀린 답: `pending → payment_failed` (그 상태는 존재하지 않음) · `pending → cancelled`
- **재고 부족** — **수량이 재고보다 많은지 검사하는 조건이 없음** → 그대로 차감, **재고 음수 가능**.
  주문은 201, `pending`으로 저장. (예: monitor 재고 2 → 수량 5 주문 → 재고 −3)
  - ✕ 틀린 답: "재고 부족 주문은 거절된다" (차단 검사가 없다)

## 2. 첫 응답 검토 — 네 가지가 분리됐나

⚠️ **강사가 결과를 받으면 이 네 개의 분리를 본다. 안 되면 다음 단계로 안 넘어간다.**

1. **상태 ↔ 저장** — 특히 실패 행. 맞는 표현: "결제 직전 `pending`, 실패 처리 후 **주문이 삭제돼
   저장된 상태가 없다**". 틀린 표현: "결제 후 상태는 payment_failed / cancelled".
2. **응답 ↔ 저장** — HTTP 200이라고 성공이 아니다. 실패의 현재 결과는 **「200 + `{ok:false}`」와
   「주문 삭제」가 동시에** 존재. 응답 코드만 보고 성공이라 쓰면 안 됨.
3. **주문 상태 ↔ 재고** — 재고 부족은 주문 상태가 아니다. 따로 적는다: 주문 상태 `pending` /
   재고 값 음수 가능.
4. **코드 ↔ 정책** — 아래가 현재 동작 표에 들어가면 안 된다(이건 요청·미결 정책이다):
   payment_failed로 보존해야 · 재결제 허용해야 · 실패 응답 402여야 · 관리자에 사유 보여줘야 ·
   성공 시점에 재고 차감해야.

### 문제 있을 때 후속 요청 (돌아다니며 잡을 것)

- **실패를 `payment_failed`로 적음** → "실패 처리 후 `src/payments.ts`에서 `orders` Map에 주문이
  남는지 확인하고, 결제 직전 상태와 실패 후 저장 상태를 구분해. 원하는 상태는 아직 쓰지 마."
- **재고 부족이 거절된다고 적음** → "`src/orders.ts`에서 재고와 요청 수량을 비교하는 조건이 실제로
  있는지 찾고, 응답·주문 상태·차감 후 재고를 구분해."
- **재고가 결제 성공 시 차감된다고 적음** → "`orders.ts`·`payments.ts`에서 stock을 바꾸는 코드를
  찾아 주문 생성 시점과 결제 시점을 구분해."
- **실패 후 관리자 목록에 표시된다고 적음** → "실패 처리 후 주문이 남는지 확인하고, `admin.ts`가
  어떤 주문 집합을 순회하는지 연결해서 설명해."
- **현재 테스트가 실패 흐름을 검증한다고 적음** → "`tests/orders.test.ts`가 쓰는 카드 토큰과
  assertion을 확인해. 파일이 존재한다는 사실과 그 흐름을 검증한다는 주장을 구분해."
- **사실과 기대가 섞임** → "현재 코드로 확인되는 것과 요청 문서의 기대를 분리해. 표엔 src·tests에서
  확인되는 것만."

## 3. 근거 감사시키기 (Sol)

초안이 괜찮아 보이면 **한 번 더 근거를 감사**하게 한다. (자기 결과를 근거로 다시 대조 — 4강
E1 셀프 리뷰와 같은 도구.)

```
목표: 방금 작성한 현재 동작 표의 각 주장을 실제 코드 근거와 다시 대조한다
문맥: 직전 표와 E1의 관련 파일 후보
제약: 새 정책이나 수정 제안을 추가하지 말고 파일도 수정하지 않는다
완료 조건: 근거 없는 주장·추정·상태와 저장 여부가 섞인 표현을 찾아 수정하고 각 행에 근거 파일을 붙인다
```

기대 근거: `store.ts`(상태 타입·저장소) · `orders.ts`(생성·즉시 차감·pending) · `payments.ts`(성공
상태 변경·실패 기록·**실패 시 삭제**·응답) · `admin.ts`(저장된 주문만 변환) · `orders.test.ts`(테스트
범위). `server.ts`·`package.json`·`tsconfig.json`은 이 표의 핵심 근거가 아닐 수 있다 — 억지로 다 넣지 않는다.

## 4. 사람 확인 (Human Gate)

⚠️ **표가 정제되면 강사가 승인하고서야 기록으로 넘어간다.** 핵심 확인:

- 세 행 다 있고, 각 행에 시작 조건·현재 응답이 있나
- 처리 전후 주문 상태가 구분됐나 · 상태와 저장 여부가 구분됐나
- 재고 변경 시점·결과가 있나 · 후속 조회 결과가 있나 · 코드 근거가 붙었나
- **정책·수정 제안이 없나** · **실패를 payment_failed로 가정 안 했나** · **재고 부족이 거절된다고 가정 안 했나**

> "현재 코드 기준 세 케이스가 사실과 맞게 분리됐습니다. 이 표를 E2 현재 동작 기준으로 **승인**합니다.
> 아직 정책 결정이나 수정 범위로는 안 넘어갑니다."

## 5. 계획 문서에 기록 (Default mode · Terra)

표 헤더: `케이스 | 시작 조건 | 현재 응답 | 처리 후 주문 상태 | 주문 저장 여부 | 재고 변화 | 후속 조회 | 코드 근거`

## 6. 검증 (Luna)

기록 후 파일은 안 고치고 검증만 시킨다:

```
제약: 어떤 파일도 수정하지 않고 앱 테스트도 실행하지 않는다
완료 조건: 세 케이스 존재·사실과 기대 분리·근거 연결·src와 tests 무변경 여부를 각각 보고한다
```

⚠️ **무변경 확인은 `git status --short -- src tests` 로 한다 — 출력이 없어야 한다.** `git diff --stat`은
새 미추적 파일을 놓칠 수 있어서 `status --short`를 같이 쓴다.

# E3 — 수정·제외 범위 정하기 (약 12~15분) · 클립 3

이 강의의 클라이맥스다. E1은 「어떤 파일이 관련 있나」, E2는 「지금 어떻게 도나」를 사실로 모았다.
E3는 **처음으로 사람이 정책을 결정하는 자리**다 — 2강에서 물음표로 남기고, 3강 human gate로
지키고, 4강 Rules로 「임의로 정하지 마」 막아 온 그 질문에, 드디어 사람이 답한다. Codex는 결정
자료를 정리하고, 사람의 결정을 구현 전 계획으로 번역한다.

두 가지만 미리 잡고 간다. 첫째, **다 답하지 않는다** — 이번 요청에 필요한 것만 정하고 나머진
「제외」로 미룬다. 이 결정은 `notes/` 작업별 계획에만 남고, 도메인 전체 영구 정책은 7강에서 만든다.
둘째, **재고 부족은 정책이 아니라 버그다** — 「정할」 게 아니라 「고칠」 것이라 pending-decisions에
없는 게 맞고, E3에선 결함으로 발견해 수정 범위에 넣는다.

- 모델: 결정 자료 정리 Terra · 정책 결정은 사람 · 범위 번역 Sol · 기록 Terra · 확인 Luna
- 시작 상태: 같은 Task. plan에 `## 관련 파일 후보`·`## 현재 동작`이 있고, `## 수정 범위`·
  `## 제외 범위`는 아직 없다. src·tests 무변경

## 여는 말

> "지금까지 Codex가 코드를 읽고 사실을 정리했죠. 근데 사실을 안다고 Codex가 제품 정책까지 정하는
> 건 아니에요. 재결제를 허용할지, 실패를 어떤 상태로 남길지 — 이건 코드에 답이 없어요. 사람이
> 정하는 겁니다."

> "2강에서 이 질문들 남겼고, 3강에선 human gate로 지켰고, 4강에선 Rules로 임의 결정을 막았죠.
> 이제, 5강에서 사람이 답합니다."

## 1단계 — 결정할 정책 회수하기 (Terra)

바로 수정 범위를 쓰지 않는다. 먼저 Codex에게 **미결 질문과 각 결정이 코드에 미치는 영향**을
정리하게 한다. 답을 고르는 게 아니라, 사람이 고를 수 있게 자료를 만드는 단계다.

`@notes/pending-decisions.md`, `@notes/task-boundary.md`, `@notes/order-status-request.md`,
`@notes/order-status-plan.md`를 붙이고:

```
목표: 이번 요청의 수정 범위를 확정하기 위해 사람이 결정할 정책을 정리한다.
문맥: @notes/pending-decisions.md @notes/task-boundary.md @notes/order-status-request.md @notes/order-status-plan.md를 사용하고, ## 관련 파일 후보와 ## 현재 동작은 다시 조사하지 않는다.
제약: 질문의 답이나 수정·제외 판단을 대신 정하지 않는다. 기존 질문만 복사하지 말고, 각 선택이 E2의 어느 현재 동작과 관련 파일에 영향을 주는지 설명한다. E2에서 드러났지만 pending-decisions.md에 없는 결정이 있다면 별도로 표시한다. 파일은 수정하지 않는다.
완료 조건: 이번 요청에서 지금 결정해야 할 질문과 나중으로 미룰 수 있는 질문을 사람이 판단할 수 있는 결정 자료를 채팅에 제시한다.
```

Codex가 도는 동안 할 말:

> "여기서 관련 파일을 다시 찾는 거 아니에요. E1에서 끝냈죠. 현재 동작도 다시 안 씁니다 — E2
> 결과를 그대로 입력으로 써요. Codex가 지금 하는 건 **질문이랑 코드 영향을 연결하는 것**입니다.
> 상태 범위를 payment_failed로 정하면 어떤 파일이 영향받는지, 재결제를 허용하면 어떤 후속 흐름이
> 붙는지 — 그걸 보여줘야 해요."

결과는 결정 항목 표로 나온다(실패 상태 범위 / 실패 응답 / 재결제 / 관리자 정보 / 검증 범위 /
**재고 부족 주문 처리**). 마지막 「재고 부족」은 pending-decisions에 없던 항목이다.

> "여기 재고 부족 보세요. 우리가 2강에서 물어본 질문이 아니에요. E2에서 재고가 음수 되는 걸
> 확인했으니까, Codex가 이걸 **별도 결함으로** 잡아낸 겁니다. 정책 질문이 아니라 버그예요."

빠르게 확인할 것 — 답을 대신 골랐나 · 질문만 복사했나 · E2 동작과 연결됐나 · **재고 부족 결함이
빠졌나.** 빠졌으면 짧게 되짚어 준다: "`## 현재 동작`에서 확인된 결함, 특히 재고 부족 행이 범위
결정에 어떤 영향을 주는지 보완해 줘. 답은 대신 고르지 말고."

## 2단계 — 사람이 정책 결정하기 (사람이 직접)

이제 사람이 답한다. Codex한테 추천안을 고르라는 게 아니고, 모든 정책을 영구 확정하는 것도 아니다.
이번 요청에 필요한 것만 정하고 나머진 미룬다.

강사가 직접 입력한다 — pending-decisions에 대한 답, 딱 네 줄:

```
실패 결제 상태 범위에 payment_failed만 추가하고 refunded는 뺀다.
관리자 목록의 실패 정보 범위를 상태, 금액, 시각 모두 표시한다.
테스트 범위는 완료 조건 네 흐름만.
결제 실패 API 응답은 402 Payment Required와 실패 정보.
```

설명하는 대본:

> "상태 범위는 payment_failed만, refunded는 이번에 뺍니다. **payment_failed를 추가한다는 건,
> 실패 주문을 삭제하지 않고 그 상태로 남긴다는 뜻이에요** — 지금은 삭제되니까요."

> "실패 응답은 402로 바꿉니다. 지금은 실패인데 200을 돌려주잖아요, 성공 코드로. 그게 이 요청이
> 나온 이유 중 하나였죠. 실패는 실패 코드로. 관리자 목록엔 실패 주문의 상태·금액·시각을 다 보이게
> 하고, 테스트는 이번에 바꾼 네 흐름만 잡습니다."

여기서 짚을 게 하나 있다. **재고 부족 차단은 이 목록에 없다.**

> "보면, 재고 얘기가 없죠? 일부러 그래요. 음수 재고는 제가 **정할 정책이 아니라 고칠 버그**예요.
> 코드에서 확인한 결함이라 pending 질문에도 없었고요. 이건 제가 여기서 답으로 치는 게 아니라,
> 다음 단계에서 E2 현재 동작의 결함으로 수정 범위에 들어갑니다. **정할 건 정하고, 고칠 건
> 고친다** — 성격이 다른 거예요."

> "그리고 재결제는요? **답을 안 했죠. 안 정한 건 자동으로 미뤄집니다** — 4강 Rules가 Codex한테
> 미결 정책을 임의로 정하지 말라고 했으니까, 안 정한 재결제·refunded는 그대로 제외 범위로 가요.
> 다 답할 필요 없어요. 이번 요청에 필요한 것만."

아직 파일은 안 고친다. 사람 답을 입력했어도, Codex가 이 결정과 E2 결함을 수정·제외 범위로
제대로 번역했는지 먼저 확인하고 기록한다.

## 3단계 — 정책과 결함을 작업 범위로 번역하기 (Sol)

입력이 두 개다 — 방금 사람이 확정한 정책, 그리고 E2에서 확인한 결함. 목표에 둘 다 적는다.

```
목표: 방금 사람이 확정한 정책과 현재 동작에서 확인된 결함을 구현 전 수정 범위와 제외 범위로 정리한다.
문맥: 사람의 결정과 @notes/order-status-plan.md의 ## 관련 파일 후보·## 현재 동작을 사용한다.
제약: 새 파일을 찾거나 기존 후보를 다시 분류하지 않는다. 같은 사용자 동작을 파일별로 중복하지 말고, 각 동작에 관련 파일과 책임 경계를 연결한다. 사람이 미룬 정책은 임의로 보완하지 않는다. 구체적인 구현 방법과 테스트 케이스는 작성하지 않고 파일도 수정하지 않는다.
완료 조건: 수정 범위에는 확정된 변화·현재 동작과의 차이·관련 파일·완료 경계가 있고, 제외 범위에는 미룬 정책 또는 유지할 구조·미루는 이유·현재 유지할 동작이 있다.
```

Codex가 도는 동안 할 말:

> "「파일별로 뭘 고친다」를 바로 나열하면 한 기능이 여러 작업처럼 부풀어요. 예를 들어 실패 주문
> 보존은 상태 타입, 결제 처리, 주문 조회에 다 걸쳐 있죠. 파일은 셋인데 사용자 눈엔 하나의
> 변화예요. 그러니 **먼저 바꿀 동작을 묶고, 그 밑에 파일을 답니다.**"

수정 범위는 대략 이 네 갈래로 나와야 한다:

- **실패 주문 보존** — 삭제 안 함, payment_failed로 남김, 이후 조회 가능 (store·payments·orders)
- **실패 응답 402** — 실패 시 402 + 실패 정보 반환, 200+{ok:false}에서 바뀜 (payments)
- **재고 부족 차단·차감 시점** — 저장·재고 변경 전 차단, 성공/실패 재고 결과 구분 (orders·payments·store)
- **관리자 노출** — 실패 주문이 목록에 남고 상태·금액·시각 표시 (admin·payments·store)

제외 범위는 사람이 실제로 미룬 것만: refunded · 재결제 · (현재 구조를 벗어나는 확장). DB·관리자
UI·외부 시스템 같은 걸 Codex가 상상해 늘어놓으면 안 된다 — 「현재 구조 유지」 경계면 충분하다.

## 4단계 — Human Gate에서 범위 검토하기 (사람)

여기 게이트는 「Codex가 조사를 잘했나」가 아니라 **「사람 결정이 계획에 정확히 반영됐나」**를 본다.

확인할 것:

- 수정 범위에 payment_failed 보존 · 402 응답 · 재고 부족 차단 · 관리자 상태·금액·시각이 다 있나
- 같은 동작이 파일별로 반복되지 않았나, 관련 파일이 E1 후보 안에서 연결됐나
- 제외 범위에 refunded·재결제가 미뤄졌나, 유지 구조가 불필요하게 부풀지 않았나
- 구현 방법·함수 순서·코드 조각·테스트 케이스가 안 들어갔나, 파일은 무변경인가

어긋나면 짧게 되돌린다:

- 재고 부족이 빠졌으면 → "사람 결정뿐 아니라 `## 현재 동작`의 결함도 반영해. 구현 방법은 쓰지 말고."
- 같은 변경이 파일별로 반복되면 → "파일 말고 사용자 동작 기준으로 묶어."
- 미룬 정책(refunded·재결제)을 Codex가 정해 버렸으면 → "그건 제외 범위로 되돌려. 임의로 고르지 마."
- 제외 범위가 과하게 커지면 → "실제 등장한 인접 작업과 사람이 미룬 것만. 새로 상상하지 마."

문제없으면 승인 문장을 **기록 계약과 함께** 보낸다:

> "수정 범위와 제외 범위를 승인합니다. 이 결과를 기준으로 계획 문서에 기록해 줘."

## 5단계 — 승인한 것만 기록하기 (Terra) · 확인 (Luna)

```
목표: 사람이 승인한 수정 범위와 제외 범위를 notes/order-status-plan.md에 기록한다.
문맥: 방금 승인한 수정 범위·제외 범위와 기존 @notes/order-status-plan.md를 사용한다.
제약: 기존 ## 관련 파일 후보와 ## 현재 동작을 보존하고, ## 수정 범위와 ## 제외 범위만 추가한다. 사람이 미룬 정책을 임의로 보완하지 않고, 구현 방법과 구체적인 테스트 계획은 작성하지 않는다. 다른 파일은 수정하지 않는다.
완료 조건: 수정 범위마다 확정된 변화·현재 동작과의 차이·관련 파일·완료 경계가 있고, 제외 범위마다 미룬 정책 또는 유지할 구조·미루는 이유·현재 유지할 동작이 있다.
```

기록 후 파일은 안 고치고 검증만 시킨다:

```
방금 기록한 E3 결과를 검토해 줘. 기존 ## 관련 파일 후보와 ## 현재 동작이 보존됐는지,
승인하지 않은 정책이 추가되지 않았는지, 구현 방법이나 테스트 계획이 미리 들어갔는지 확인해라.
문제가 없다면 파일은 수정하지 말고 결과만 보고해 줘.
```

> 고치는지 같이 보면서 갑니다."

### 1. 재고 부족 차단 시점 정정

`[## 수정 범위에서 「주문 생성」·「재고 부족 상태에서 결제」 두 행을 가리키며]`

> "지금 계획은 재고 확인을 두 작업으로 나눠 놨어요 — 주문 생성 때는 재고를 안 건드리고, 결제
> 시점에 재고가 부족하면 막는 걸로. 근데 이걸 하나로 합칩니다. **재고 부족은 결제 시점이 아니라
> 주문을 저장하기 전에** 확인해요."

정정된 행(목표 상태):

```
| 주문 생성과 재고 부족 주문 차단 | 현재는 주문 생성 즉시 재고가 차감되고, 재고보다 많은
수량도 주문되어 재고가 음수가 됨. 확정 범위에서는 주문 생성 자체가 재고를 차감하지 않고,
재고가 부족한 주문은 저장과 재고 변경 전에 차단함 | src/orders.ts, src/store.ts |
재고 충분: pending 저장, 생성만으로 재고 불변 / 재고 부족: 주문 미저장, 재고 불변 |
```

> "완료 경계도 같이 바뀝니다. 재고가 충분하면 pending으로 저장되고 재고는 그대로. 부족하면
> 주문을 저장하지도, 재고를 건드리지도 않아요."

### 2. 관리자 조회에 결제 실패 사유 추가

`[관리자 실패 주문 조회 행을 가리키며]`

> "관리자 조회는 E3에서 실패 상태·금액·시각까지만 적었죠. 여기에 **결제 실패 사유의 저장과
> 노출**을 더합니다."

정정된 완료 경계: `주문이 관리자 목록에 포함되고 실패 상태·금액·시각·결제 실패 사유가 확인됨`

정정된 행(목표 상태):

```
| 관리자가 실패 주문 조회 | 현재는 실패 주문이 삭제되어 목록에 안 나타남. 확정 범위에서는
실패 주문을 상태·금액·시각·결제 실패 사유와 함께 표시 | src/admin.ts, src/store.ts |
주문이 관리자 목록에 포함되고 실패 상태·금액·시각·결제 실패 사유가 확인됨 |
```

> "여기서는 **실패 사유를 노출한다는 책임 경계까지만** 확정합니다. 테스트에서 구체적인 필드명·값을
> 비교하려면 그 계약은 또 사람이 정해야 해요 — 그건 E4에서."

### 3. 제외 범위에서 충돌 항목 제거

`[## 제외 범위를 가리키며]`

> "수정 범위가 바뀌었으니, 거기랑 부딪히는 제외 항목도 빼줘야 합니다."

- **「재고 부족 결제의 구체적 응답」 삭제** — 재고 부족을 주문 저장 전에 차단하기로 했으니, 「결제
  시점 응답」을 논하던 이 항목은 더 이상 현재 범위와 안 맞는다.
- **「결제 실패 사유 표시」 삭제** — 실패 사유를 수정 범위에 넣었으니, 그걸 제외한다는 행은 모순이다.

> "정정하고 나면 제외 범위엔 이것만 남아요 — 주문 환불, 주문 취소, 재결제 이후 상태 처리, 라우팅·저장 기술 변경."

### 4. 완료 여부 검증 행을 E3에서 제거 (→ E4)

`[## 수정 범위의 「완료 여부 검증」 행을 가리키며]`

> "마지막으로, 수정 범위에 있는 「완료 여부 검증」 행을 뺍니다. 테스트랑 타입 검사는 **사용자
> 동작의 수정 범위가 아니라, 지금 시작할 E4의 테스트·검증 계획**에 들어갈 내용이거든요."

> "`tests/orders.test.ts`의 구체적 검증 책임이랑 `npm test`·`lint`·`typecheck` 실행 계획은 E4에서
> 다시 씁니다."
