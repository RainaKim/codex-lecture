# 4강 스피커 노트 — Codex가 먼저 읽어야 할 기준 만들기

Part 1 · Chapter 1 · 4강 · 이론 + 실습 · 약 45분 · 20장 · 클립 4개

## 이 노트 쓰는 법

- 괄호 안 시간은 목표치다. 네 클립은 각각 약 15 · 9 · 8 · 13분이고, 밀리면 이론에서 줄이고
  실습은 지킨다.
- 인용부호 안은 그대로 읽어도 되는 문장이다. 대본이 아니라 뼈대니까 말투는 편한 대로 바꾼다.
- ⚠️ 표시는 놓치면 뒤가 어긋나는 지점이다.
- 실습 지시서는 `labs/lecture04/README.md`, 입력 재료는 2강 `notes/` 세 파일과 3강
  `notes/task-boundary.md`다. 화면에는 슬라이드를 띄우고, 수강생은 README를 따라간다.
- 오늘 산출물은 **파일 하나**다 — repo 루트의 `AGENTS.md`. 실습 네 번이 같은 파일에 섹션을
  하나씩 채운다. 3강이 `task-boundary.md` 하나를 키운 것과 같은 방식이다.
- 자동 검증은 `node labs/tools/check.mjs 04`.
- **프롬프트는 미리 붙여넣지 않고 화면에서 직접 친다.** 2·3강에서 쓴 `목표 / 문맥 / 제약 /
  완료 조건` 네 줄 계약을 오늘도 그대로 쓴다. 계약 원문은 각 실습 절에 있고, 부록에 모아뒀다.
  근거는 『Codex로 일하는 법』 8장.
- 오늘 4강은 **1강 챕터의 마지막 강의**다. 1~3강에서 사람이 매번 붙여 주던 기준을 파일로
  옮겨, agent가 시키지 않아도 먼저 읽게 만드는 날이다. 이 전환이 오늘 전체의 축이다.

### 실습에서 쓸 모델 tier (강의 운영 원칙)

실습에서 Codex를 돌릴 때 단계마다 모델 tier를 바꾼다. 세 tier로 부른다 —
**Sol**(강한 추론) · **Terra**(일반 작업) · **Luna**(경량).

- **강의 설계·스피커 노트·실습 back-and-forth 설계** — Sol. (강사가 준비할 때 쓰는 것)
- **학습자가 Codex에게 실제 문서·코드를 만들게 하는 실행** — Terra가 기본
- **이미 승인된 명령의 반복 실행, 파일 존재 확인, 정해진 형식 검사** — Luna
- **지속 지침·정책·보안·배포·커밋 범위처럼 작은 실수도 비싼 작업** — 짧아도 Sol, 최소 Terra

실습별 실행 모델은 각 실습 절에 적어뒀다. 대략 E1 실행은 Terra 한 큐, E2~E4는 제안 단계에서
판단이 무거워지면 Terra로 시작해 필요할 때 Sol로 올리고, `check.mjs` 같은 확정된 검사는 Luna로
내린다. **강사가 이 노트·실습을 설계할 때 쓰는 모델은 Sol이다.**

### 자동 검증 (강사가 먼저 알고 있을 것)

`node labs/tools/check.mjs 04`는 두 가지를 본다.

- 루트에 `AGENTS.md`가 있는가
- 그 안에 헤딩 다섯이 정확히 있는가 — **대소문자·영문까지 맞아야 한다**

```
## Project Overview
## Before Editing
## Commands
## Rules
## Before Final Response
```

⚠️ **3강과 달리 `src/`·`tests/` 검사는 없다.** 오늘은 코드를 만드는 강의가 아니라 기준 문서를
만드는 강의라, 검증 규칙(`l04.json`)에 코드 검사가 꺼져 있다. 그래도 오늘도 앱 코드는 한 줄도
안 고친다 — 습관을 유지한다.

⚠️ **통과가 잘 썼다는 뜻은 아니다.** 헤딩 다섯이 있고 본문이 조금만 있으면 통과한다. 내용이
비었거나 소망을 사실처럼 적어도 통과한다. 내용은 사람이 본다 — 각 실습 검수 항목에서 짚는다.

## 04 프롬프트는 오늘 할 일, AGENTS.md는 늘 지킬 일 (2.5분)

⚠️ **오늘의 lesson 한 장이다.** 프롬프트와 AGENTS.md가 어떻게 다른지를 세 축으로 가른다.
**파일에 어떻게 적는지는 여기서 안 한다** — 실습 ①의 자리다.

### 도입 — 왜 굳이 파일로 옮기나

> "이런 생각 드실 수 있어요. 매번 프롬프트에 적으면 되지, 왜 파일로 옮기냐. 그래서 이 둘이
> 뭐가 다른지부터 봅니다."

세 축을 위에서 아래로 읽는다. **가운데 「비교 축」 열이 이 장의 뼈대다.**

> "첫째, 읽히는 시점. 프롬프트는 **사람이 붙여 준 세션에서만** 읽힙니다. AGENTS.md는 **매
> 세션 시작 때, 시키지 않아도** 읽혀요."

> "둘째, 전달하는 주체. 프롬프트는 **사람**이 나릅니다. 빠뜨린 날은 그냥 규칙이 없는 거죠.
> AGENTS.md는 **repo**가 나릅니다. 커밋에 실려서 같이 가니까요."

> "셋째, 바꾸는 방법. 프롬프트는 사람마다 문장이 조금씩 달라집니다. AGENTS.md는 **커밋으로만**
> 바뀌어요. 누가 언제 왜 바꿨는지 이력이 남습니다."

⚠️ **둘째 축에서 멈춘다. 「사람이 나른다」가 왜 문제인지 한마디 붙인다.**

> "사람이 나른다는 게 핵심이에요. 사람은 빠뜨립니다. 바쁜 날, 새벽에, 새 팀원이 왔을 때.
> **한 번이라도 빠뜨리면 그 세션은 기준 없이 도는 겁니다.** 파일은 안 빠뜨려요."

## E1 실습 1 (4분)

⚠️ **E1은 한 큐로 간다. back-and-forth는 여기 안 쓴다.** Project Overview는 근거가
`README.md`와 소스 몇 개에 명확하고 결과도 2~4문장이라, 제안·리뷰·수정을 나누는 게 오히려
낭비다. **한 프롬프트로 생성하고 사람이 30초 검토한다.** 대화형 흐름은 판단이 진짜 어려운
E2~E4에서 보여준다 — 쉬운 건 한 방에, 어려운 건 왕복으로.

⚠️ **모델은 Terra(일반 작업).** 파일을 읽고 짧은 지침 문서를 만드는 일이고, 범위가 명확하고
오류도 즉시 눈에 띈다. Project Overview도 지속 지침이지만 「최소 Terra」 선에 딱 맞는 예다.

큐 장을 띄우고 한 줄만 읽는다.

> "다섯 헤딩 뼈대를 세우고 Project Overview를 채웁니다. 이건 근거가 분명하니 **한 번에
> 만들고, 제가 30초 봅니다.**"

### 네 줄 계약 — 한 큐지만 형식은 2·3강 그대로, 화면에서 직접 친다

```
목표: root AGENTS.md 를 생성하고 ## Project Overview 만 채운다
      2~4문장으로 저장소 목적 · 넓은 기술 구성 · 데이터 저장 방식을 적는다
문맥: README.md · package.json · src/server.ts · src/store.ts
      — 현재 파일로 확인되는 사실만 쓴다
제약: ## Project Overview 외 다른 헤딩은 만들지 않는다
      명령 · API 경로 · 포트 · 초기 상품 · 상태 값 · 결제 실패 세부 동작을 쓰지 않는다
      아직 결정되지 않은 정책을 쓰지 않는다
완료 조건: ## Project Overview 만 있고 본문이 2~4문장이다
          사용한 근거 파일과 의도적으로 제외한 정보 종류를 보고한다
```

> "형식은 지난 시간이랑 같아요 — 목표·문맥·제약·완료 조건. 다만 오늘 E1은 **한 번에** 칩니다.
> 근거가 분명하니 왕복이 필요 없어요."

⚠️ **완료 조건 둘째 줄(근거 파일 + 제외한 정보 보고)이 이 계약의 장치다.** 30초 검토를 이걸로 한다.

> "완료 조건 마지막 줄 보세요. 만들고 나서 **어느 파일을 근거로 썼는지, 뭘 일부러 뺐는지**
> 보고하게 했어요. 이게 있으면 제가 결과물을 처음부터 뜯어볼 필요 없이, 그 보고만 보고
> 사실인지 판정합니다."

엔터. **예상 결과** (실제 문구는 리허설로 대조):

```
## Project Overview

order-ops는 주문 생성, 결제, 재고, 관리자 조회가 연결된 TypeScript API를
```

실습 중 여기만 보면 된다. **붙여넣지 말고 친다.** 각 실습 절에 칸마다 무슨 말을 붙일지 적어뒀다.
근거는 『Codex로 일하는 법』 8장·11장 — 요청은 작업 계약이고, 매번 설명하던 기준은 repo 문서로
옮긴다.

### E1 — Project Overview (한 큐, Terra)

E1은 계약을 한 번에 친다. 근거가 명확하고 결과가 짧아 왕복이 필요 없다.

```
목표: root AGENTS.md 를 생성하고 ## Project Overview 만 채운다
      2~4문장으로 저장소 목적 · 넓은 기술 구성 · 데이터 저장 방식을 적는다
문맥: README.md · package.json · src/server.ts · src/store.ts
      — 현재 파일로 확인되는 사실만 쓴다
제약: ## Project Overview 외 다른 헤딩은 만들지 않는다
      명령 · API 경로 · 포트 · 초기 상품 · 상태 값 · 결제 실패 세부 동작을 쓰지 않는다
      아직 결정되지 않은 정책을 쓰지 않는다
완료 조건: ## Project Overview 만 있고 본문이 2~4문장이다
          사용한 근거 파일과 의도적으로 제외한 정보 종류를 보고한다
```

> **완료 조건 둘째 줄** — "근거 파일과 제외한 정보를 보고하게 한다. 이게 30초 검토의 재료다."
> **30초 검토** — Project Overview만 있나 · 미정 정책 안 섞였나 · README·store.ts로 뒷받침되나.
> 문제 있으면 그때만 한 번 고치게 한다.

### E2 — Before Editing + Commands

```
목표: ## Before Editing 에 수정 전에 읽을 것과 계획 기준을 적고
      ## Commands 에 이 repo 의 검증 명령을 적는다
문맥: labs/CONVENTIONS.md — 산출물 위치 규약
      package.json 의 scripts
      notes/ 의 2·3강 산출물 — 미결정 질문과 작업 경계가 여기 있다
제약: Before Editing 은 읽을 것으로 시작해
      「코드를 고치기 전에 계획을 먼저 적는다」로 끝난다
      읽을 것에는 README.md · labs/CONVENTIONS.md ·
      고치려는 코드의 관련 테스트 · notes/ 의 미결정 질문을 넣는다
      Commands 에는 package.json 에 있는 명령만 적는다 — 새 명령을 만들지 않는다
      명령마다 무엇을 확인하는 명령인지 한 줄씩 붙인다
완료 조건: 두 섹션이 채워져 있고 labs/CONVENTIONS.md 참조가 있으며
          Commands 의 명령이 전부 package.json scripts 에 실제로 있다
```

> **제약 셋째 줄** — "있는 명령만. `preflight` 같은 걸 지어낸다. 실물은 test·lint·typecheck."
> **완료 조건 마지막 줄** — "agent가 자기가 적은 명령을 `package.json`이랑 대조하게 만든다."

### E3 — Rules

```
목표: ## Rules 에 이 repo 에서 항상 걸리는 금지 규칙을 적는다
문맥: notes/task-boundary.md 의 ## 아직 하지 말 것 · ## 멈춤 조건
      — 3강에서 쓴 원본이 재료다
      notes/pending-decisions.md — 임의 확정을 막을 질문 목록
제약: 네 가지를 반드시 담는다 —
      미결정 정책을 임의로 확정하지 않는다 ·
      오류를 삼키는 silent fallback 을 추가하지 않는다 ·
      테스트 없이 주문 상태 처리를 바꾸지 않는다 ·
      실제 결제 연동을 추가하지 않는다
      규칙마다 금지 행동과 이유를 한 줄로 같이 적는다
      지금 있는 v0 결함을 고치라는 지시로 바꾸지 않는다 — 고치는 건 정책 확정 뒤다
완료 조건: ## Rules 아래 금지 규칙이 네 종류 이상 있고 규칙마다 이유가
          붙어 있다 · src/ 와 tests/ 는 바뀌지 않았다
```

> **제약 「이유를 같이」** — "이유 없는 규칙은 다음 세션이 예외를 만든다."
> **제약 마지막 줄** — "규칙 쓰다 코드를 고치려 한다. 고치는 건 다음 강의부터."

### E4 — Before Final Response + 커밋

```
목표: ## Before Final Response 를 채우고 AGENTS.md 를 커밋한다
문맥: AGENTS.md 전체 — 특히 ## Commands 의 검증 명령
제약: 최종 보고 전에 할 일을 적는다 — 실행한 검증 명령과 결과를
      보고에 포함한다 · 바꾼 파일 목록을 적는다 ·
      Rules 에 걸려 멈췄으면 그 지점을 보고한다
      「통과했다」만으로는 안 된다 — 무엇을 실행해 무엇이 나왔는지가 남게 한다
      CLAUDE.md 같은 지침 파일을 같이 만들지 않는다 — 기준 문서는 하나만 둔다
      커밋은 AGENTS.md 하나만
완료 조건: 다섯 섹션이 모두 채워져 있고
          node labs/tools/check.mjs 04 가 통과한다 (파일 위치 · 다섯 헤딩)

# 커밋 뒤 — 새 Codex 세션을 열어 「지금 따르는 지침과 검증 명령을
# 요약해 줘」라고 묻는다. Rules 가 요약되어 돌아오면 기준이 읽힌 것이다
```

> **제약 「CLAUDE.md 금지」** — "친절하게 세 개를 만든다. 유지 지점이 늘면 어긋난다. 하나만."
> **커밋 뒤 절차** — "새 창에서 아무것도 안 붙이고 「지침 요약해 줘」. Rules가 오면 성공.
> 오늘 강의 전체가 이 장면을 위한 것이다."

## 연결 관계

- **1강 → 4강**: 세 실패 패턴이 오늘 규칙으로 막힌다. 「매번 재설명」→ AGENTS.md 자동 로딩,
  「바로 구현」→ Rules 첫 줄 + Before Editing 순서, 「검수 불가」→ Before Final Response
- **2강 → 4강**: `pending-decisions.md`가 Overview의 「미정은 안 적는다」와 Rules의 「임의
  확정 금지」의 재료
- **3강 → 4강**: `task-boundary.md`의 「아직 하지 말 것」·「멈춤 조건」이 Rules의 원본.
  이번 작업 경계(3강)가 repo 전체 규칙(4강)으로 승격
- **4강 → 5강**: 오늘 커밋한 `AGENTS.md`가 5강 plan-first 작업에서 처음으로 자동으로 먼저 읽힌다
- **4강 → 6·7강**: Before Editing이 참조하는 `docs/`는 6강에서 생기고, 정책 문서는 7강에서
  Rules의 「미정 정책」을 실제로 확정한다
