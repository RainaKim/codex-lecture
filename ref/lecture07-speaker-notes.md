## 이 강의가 하는 일 (여는 말 전에 강사가 잡고 갈 것)

지금까지(Chapter 1) 우리는 요청 하나를 작업 자산·workflow skeleton으로 바꿨다. 그런데 "주문이
어떤 상태를 거치는지, 결제 실패 때 뭘 남기는지, 재고를 언제 줄이는지" 같은 **도메인 판단은 아직
`notes/`에 작업별로만** 있거나 아예 없다. 7강은 그걸 **여러 작업에서 다시 읽는 `docs/` 정책으로
승격**한다. 그래야 Codex가 매번 추측하지 않고 같은 기준에서 일한다.

**모델·surface 원칙 (전 실습 관통)**
- 긴 판단·문서 작성은 **Desktop**에서. Browser·Computer Use·Scheduled는 안 쓴다.
- **정책은 사람이 정한다.** Codex가 빈칸을 대신 채우지 않는다.
- 충돌·책임 경계 판단 = **Sol** / 승인된 문서 작성 = **Terra** / 형식·경로·diff = **Luna·CLI** /
  자동 적용 확인 = **대화 맥락 없는 새 Task**.
- 각 실습은 **설계 질문 → (Sol 초안) → 사람 승인 → Terra 작성 → Luna 검증** 순서. 승인 전에는
  파일을 쓰지 않는다.

**이 대본에서 강사가 확정해 둔 결정** (Lab README의 `______` 빈칸 — 전부 강사 재량, 필요하면 바꾼다)
- E1 · `paid` 이후 취소: **환불(`refunded`)로만 처리**한다 → `paid→cancelled`는 금지, `paid→refunded` 허용.
- E2 · 재시도: **이번 정책에서는 보류**(허용하지 않음). 실패는 `payment_failed`로 보존하고 재결제는 새 주문으로.
- E3 · 제외 정보: 카드번호·카드 토큰·내부 예외.

**심화 (강사) — 왜 문서가 에이전트 성능을 올리나**
> "여기서 한 가지 짚고 갈게요. LLM은 근본적으로 **다음에 올 토큰을 확률로 예측하는** 모델이에요.
> 그래서 우리가 안 정해둔 부분은 **학습 데이터에서 '보통 그렇게들 하던' 방식**으로 메꿉니다. '결제

> 버려요. 정책 문서를 쓴다는 건 사실 **모델의 확률 분포를 우리 도메인 쪽으로 조건화(conditioning)**
> 하는 겁니다. 그래서 더 좋은 모델을 쓰는 것만큼이나, **같은 모델에게 더 좋은 컨텍스트를 주는 게**
> 결과를 안정시켜요. 오늘 만드는 세 문서가 바로 그 컨텍스트고요."

## 슬라이드 05 — 주문 상태 원칙 (이론 핵심)

이 장에서 오래 멈춘다.

> "주문은 다섯 상태를 지납니다. `pending`으로 생기고, 결제가 성공하면 `paid`, 실패하면
> `payment_failed`, 취소하면 `cancelled`, 환불하면 `refunded`. 그런데 **여기서 중요한 건
> 상태 이름이 아니에요.** 화살표에 붙은 말 — '결제 성공', '결제 실패', '환불' — 언제 넘어가는가,
> 그게 정책입니다."

> "그리고 오른쪽 회색 글씨 보세요. `payment_failed`, `cancelled`, `refunded`는 **되돌아가지
> 않는 종료 상태**예요. 이런 '허용하지 않는 전환'을 안 적어두면, Codex는 `paid`를 다시 `pending`으로
> 돌리는 코드도 아무렇지 않게 만듭니다."

⚠️ **`payment_failed`가 레드인 이유를 짚는다.** — "지금 코드(v0)엔 이 상태가 아예 없어요. 결제가
실패하면 주문을 그냥 지워버립니다. 오늘 이걸 '상태로 남긴다'로 바꾸는 게 이 강의의 핵심 중 하나예요."

하단 스트립을 읽으며 다음 장으로 넘어간다.
> "상태 이름만 적으면, 언제 그 상태로 바뀌는지는 Codex가 알아서 추측해요. 그래서 전환을 표로
> 적는데 — 그 표가 그냥 표가 아닙니다. 다음 장 보시죠."

**심화 (강사) — 열린 판단을 닫힌 분류로**
> "상태를 '다섯 개'로 못 박고 전환 규칙까지 주면, 모델이 하는 일이 **열린 판단에서 닫힌 분류로**
> 바뀝니다. 고를 수 있는 답이 유한하니 틀릴 공간 자체가 줄어요. 반대로 '상태 알아서 관리해줘'는
> 세션마다 다르게 해석합니다 — 어떤 세션은 `failed`, 어떤 세션은 `error`, 어떤 세션은 `declined`로
> 만들어서 나중에 코드가 갈라져요. 실제로 이게 팀에서 제일 흔한 사고 중 하나입니다. **선택지를
> 유한하게 못 박는 것** 자체가 에이전트를 정확하게 만드는 가장 값싼 방법이에요."

## 슬라이드 06 — 규칙에서 확인 목록으로

전이도(05)에서 한 걸음 더 — 상태가 바뀌는 규칙을 정해두면 무슨 일이 생기는지.
> "상태 변화는 두 갈래로 나뉘어요. **정상 흐름**은 코드가 그대로 따라야 하는 것 — 결제 성공하면
> paid, 실패하면 payment_failed 이런 정상적인 진행이죠. **잘못된 흐름**은 반대예요. 예를 들어
> 이미 결제된 paid를 다시 pending으로 되돌린다? 결제가 끝난 주문이 결제 전으로 돌아간다는
> 거잖아요 — **논리적으로 말이 안 되는 모순**이에요. 환불된 refunded를 다시 paid로 만드는 것도
> 마찬가지고요."

⚠️ **여기가 이 클립의 기술 포인트.**
> "오른쪽 보세요. 이 논리적 모순 하나를 크게 집었어요. 이건 코드가 **반드시 막아야** 하고, 그
> '정말 막히는지' 확인하는 지점이 하나 생깁니다 — 이걸 체크포인트라고 할게요. 나중에 구현
> 챕터에서 이 모순 하나가 그대로 확인 코드 하나로 옮겨져요."

> "그러니 지금 E1에서 상태 변화 규칙을 대충 적으면 안 됩니다. **논리적 모순을 하나 찾을 때마다
> 체크포인트가 하나 늘어나요** — 규칙을 잘 적어두면 나중에 확인이 쉬워집니다. 직접 해보죠."

**심화 (강사) — 모델은 '적힌 제약'엔 강하고 '생략된 제약'엔 약하다**
> "LLM은 **명시된 규칙에서 코드를 만드는 건 아주 잘하는데, 적히지 않은 제약을 스스로 추론하는 건
> 약합니다.** 그래서 '하면 안 되는 흐름'을 표에 안 적으면, 그걸 막는 코드도 그 반례 테스트도 그냥
> 안 생겨요 — 모델은 '아무도 그런 걸 요구 안 했으니까' 하고 넘어갑니다. 반대로 금지 규칙을 표로
> 박아두면 나중 구현 세션이 그걸 그대로 거부 코드로 옮겨요. **규칙을 적는 게 곧 스펙을 주는 것**이고,
> 스펙이 있는 순간 에이전트의 정확도가 확 올라갑니다. 우리가 지금 표를 정성껏 적는 이유예요."

## E1 실습 — 두 근거를 병렬 조사하고 전이 정책 정하기 (약 12분)

**실습 1에서 할 일 (소개)**
> "첫 실습에서는 **주문 상태 정책**을 만듭니다. 순서는 이래요. 먼저 두 개의 subagent로 **문서에 남은
> 사람 결정**과 **코드가 지금 실제로 하는 일**을 나눠서 조사합니다. 그다음 그 결과를 놓고, 아직 아무도
> 안 정한 전환 경계 — 예를 들어 결제된 주문을 취소로 볼지 환불로 볼지 — 를 **사람이 직접 결정**해요.
> 그 결정을 근거로 Codex가 `docs/order-policy.md`에 상태 정의와 전환표를 쓰고, 마지막에 우리가 그
> 문서를 직접 읽고 검증합니다."
> "정리하면 — **조사는 Codex, 결정은 사람, 작성은 Codex, 검증은 다시 사람.** 산출물은
> `docs/order-policy.md`의 상태 정의와 전환 조건이고, **앱 코드는 한 줄도 안 건드립니다.**"

**1. 왜 Subagent를 쓰는가**
> "첫 단계에선 현재 코드와 이미 내린 결정을 동시에 확인해야 합니다. 한 Task가 모든 파일을 순서대로
> 읽게 할 수도 있지만, 그러면 현재 구현과 목표 정책이 한 답변에 섞이기 쉬워요. 그래서 서로 독립적인
> 두 조사로 나눕니다. 첫 agent는 문서에 기록된 **사람 결정**을, 둘째 agent는 코드가 지금 **실제로
> 하는 일**을 확인합니다. 둘 다 정책을 결정할 권한은 없습니다."

화면에서 관련 파일을 `@`로 연결한 뒤:

```
목표: 두 subagent로 주문 상태 정책의 문서 근거와 코드 근거를 병렬 조사한다.
문맥: agent A는 @notes/pending-decisions.md @notes/order-status-plan.md, agent B는 @src/store.ts @src/payments.ts @src/admin.ts를 읽는다.
제약: 정책을 선택하거나 파일을 수정하지 말고, 두 결과를 섞지 않은 채 근거와 충돌만 보고한다.
완료 조건: 각 결과의 출처와 상태·전환·삭제 영향이 비교 가능하다. 추가 판단 항목: 실패 주문 보존 이유
```

**2. Subagent 활동을 직접 확인한다** (실행되는 동안)
> "중요한 건 agent가 두 개 보인다는 사실이 아니에요. **정말 독립적으로 나눌 수 있는 작업을
> 병렬화했는가**가 핵심입니다. 같은 파일을 두 agent에게 읽히면 비용만 두 배죠. 지금은 문서상 목표와
> 코드상 현실이라는 서로 다른 증거를 조사하니까 병렬화할 가치가 있어요."

Subagent 활동 화면에서 — Agent A가 `pending-decisions.md`·`order-status-plan.md`를 읽었나 · Agent B가 `store.ts`·`payments.ts`·`admin.ts`를 읽었나 · 둘 다 파일을 수정하지 않았나 · 각 결론에 근거 파일이 붙어 있나.

**3. 통합 결과를 읽는다 — 두 조사의 역할부터 구분**
바로 문서를 쓰지 않고 결과를 직접 읽는다.
> "두 agent 조사가 끝났어요. **Agent A는 지금까지 사람이 결정하고 계획에 남긴 내용** — 앞으로 만들
> 동작의 근거입니다. **Agent B는 현재 코드가 실제로 뭘 하는지** — 아직 안 바뀐 v0의 기준선이고요.
> 두 결과가 다르다고 곧바로 충돌은 아니에요. 현재 동작과 목표 동작이 다른 건 이번 작업에서 의도한
> 차이일 수 있습니다."

화면에서 대비를 가리킨다:
- Agent A(목표): `pending → payment_failed` 계획 · 실패 주문 보존·조회 가능
- Agent B(현재): 실패 시 상태 전환 없이 주문 삭제 · 삭제로 단건·관리자 조회에서 사라짐

> "A는 '실패 주문을 payment_failed로 보존', B는 '현재 코드가 삭제'. **이건 충돌이 아니라 목표 정책 vs
> 변경 전 코드예요.** 정책 문서를 만들 땐 둘을 섞지 말고 '현재는 이렇지만 앞으로는 이 규칙을 지킨다'는
> 경계를 분명히 만들어야 합니다."

**payment_failed를 상태로 남기는 이유** (이전 강의에서 이미 사람이 확정 — 여기서 다시 고르지 않음)
> "현재 코드는 결제 실패 '이력'은 남기면서 주문 본체는 삭제해요. 그래서 **이력만 있고 대응하는 주문이
> 없는 '고아 이력'**이 생깁니다. 이건 조회 화면에 주문 하나 안 보이는 문제가 아니에요."
> "삭제하면 세 가지를 잃습니다. 첫째 **감사 추적** — 어떤 주문에서 얼마가 언제 실패했는지 주문과
> 연결해 설명 못 함. 둘째 **재시도의 동일성** — 다음 시도가 같은 주문 재결제인지 새 주문인지 구분
> 못 함. 셋째 **관리자 정산** — 관리자 목록은 저장된 주문 기준이라 실패 건을 못 봄. 그래서
> payment_failed는 이름 추가가 아니라 **실패 주문도 생명주기의 일부로 보존한다**는 정책이에요."

**4. Human Gate — 전환을 사람이 결정한다**
상태 이름은 다섯 개로 고정: `pending`·`paid`·`payment_failed`·`cancelled`·`refunded`.

*이번에 새로 판단할 빈틈 찾기*
> "두 결과에서 아직 답 안 한 부분을 찾습니다. Agent A: refunded·cancelled는 이전 구현 요청 범위 밖.
> Agent B: cancelled는 타입엔 있지만 실제 진입 경로가 없고, refunded는 타입에도 없음."
> "여기 중요한 구분 — **'이번 구현에서 제외했다'와 '도메인 정책에 존재하지 않는다'는 다른 말입니다.**
> 5강 계획은 결제 실패 개선 요청 하나의 범위였어요. 그래서 환불 '구현'을 안 한 건 맞습니다. 하지만
> 7강은 주문 도메인이 앞으로 지킬 지속 정책을 정의해요. 지금 구현 안 해도 refunded가 어떤 상태인지,
> 어디서 들어올 수 있는지는 정할 수 있습니다."

*학습자에게 판단 질문* (잠시 생각할 시간)
> "이미 paid된 주문을 고객이 취소하고 싶대요. 바로 cancelled로 바꿔도 될까요? 아니면 결제 이후엔
> refunded로만 가야 할까요?"
> "화면 문구로만 보면 둘 다 돼 보여요 — 고객은 취소했으니 cancelled라 부를 수도. 하지만 **상태는
> 화면 문구가 아니라 시스템이 기억해야 하는 사실입니다.**"

*두 선택지 비교*
> "① `paid → cancelled` 허용: '취소됐다'는 남지만, 상태만 봐선 결제 전 취소인지 돈 돌려준 뒤
> 취소인지 몰라요. 운영자가 결제 이력을 따로 뒤지고 환불 실제 수행도 별도로 확인해야 합니다."
> "② cancelled/refunded 책임 분리: 결제 전 중단 = `pending → cancelled`, 결제 후 환불 =
> `paid → refunded`. **최종 상태만 봐도 금전 처리 여부가 구분됩니다.**"
> 확인 질문: "관리자 목록에 cancelled만 보일 때, 이 주문이 한 번이라도 결제됐는지 바로 알 수
> 있나요?" → (없다) → "그래서 결제 후 금액 반환은 일반 취소와 분리하는 게 낫습니다."

*사람의 정책 결정 입력* — ⚠️ **Codex가 고르는 값이 아니다. 지금 사람이 경계를 확정한다:**
- `paid` 이후 경계: **`paid`는 `cancelled`로 전환하지 않고, 금액을 되돌릴 때만 `refunded`로.** `cancelled`는 결제 전 `pending` 주문에만.
- 이유: 결제 성공 뒤엔 금전 처리 이력이 남아야 하므로, 단순 취소와 환불을 같은 상태로 섞으면 안 된다.

> "문장만 넣은 게 아니라 **허용 전환과 금지 전환을 동시에** 정했어요."

| 시작 상태 | 이벤트 | 종료 상태 | 판단 |
| --- | --- | --- | --- |
| pending | 결제 전 취소 | cancelled | 허용 |
| paid | 환불 완료 | refunded | 허용 |
| paid | 일반 취소 | cancelled | 금지 |

*다음 작업으로 넘기기*

> **Codex가 정책을 정한 게 아니에요. Codex는 조사했고, 사람은 경계를 결정했으며, 다음엔 그 결정을
> 문서 구조로 옮기는 겁니다.**"

## 슬라이드 07 — 결제 실패 주문을 지우면 무엇이 사라지나 (클립 1 마무리)

> 되살려요."

> "오른쪽 — `payment_failed`로 **상태만 바꿔** 남기면 이력도 남고, 재시도도 안전하고, 정산도 됩니다.
> 그래서 실패를 상태로 남기는 건 취향이 아니라 **기술적 필연**이에요. 이게 다음 클립의 결제·재고

> 불가능해져요. 실제 사례로 — 실패 주문을 지워버리면, 고객이 '카드에선 돈이 빠졌는데 주문이 없다'고
> 문의했을 때 CS가 **그 케이스를 재현조차 못 합니다.** 그래서 payment_failed는 취향이 아니라 운영

## 슬라이드 08 — 결제/재고 원칙

> "정본 규칙 세 줄이에요. 결제가 성공하면 그때 재고를 줄인다. 실패하면 재고를 건드리지 않는다.
> 재고가 부족하면 주문을 만들기 전에 막는다. **재고는 결제가 성공한 뒤에만 줄어든다** — 이게 핵심이고,
> v0는 지금 이걸 안 지켜요(음수 재고까지 허용). 오늘 문서로 못 박습니다."

**심화 (강사) — 재고 차감 '시점'이 왜 정책인가**
> "재고를 언제 줄이느냐가 왜 이렇게 중요하냐면 — 결제 전에 줄이면 실패·이탈 주문이 재고를 갉아먹고,
> 성공 후에만 줄이면 재고와 매출이 정합을 유지해요. 이건 동시성(여러 주문이 같은 상품을 노릴 때)과
> 롤백(결제 실패 시 되돌리기) 문제와 직결됩니다. 에이전트 관점에서 — 이 타이밍 규칙을 문서에 박아
> 두면 구현 세션이 **경합 지점과 롤백 지점을 놓치지 않아요.** 안 박아두면 '적당히' 처리해서 음수
> 재고 같은 버그가 나옵니다. 지금 v0가 딱 그 상태고요."

## 슬라이드 09 — 결제와 재고는 다른 판단

> "그런데 왜 굳이 파일을 둘로 나눌까요? 이유는 세 가지예요."

> "첫째, **결제 규칙과 재고 규칙은 서로 다른 이유로, 다른 때 바뀝니다.** 결제 규칙은 PG사·카드사
> 사정이나 402 같은 응답 정책 때문에 바뀌고, 재고 규칙은 '언제 차감하나, 부족하면 어디서 막나'
> 같은 판매·창고 사정으로 바뀌어요. 바뀌는 이유가 다르면 파일도 따로 두는 게 맞습니다."

> "둘째, **한쪽을 고쳐도 다른 쪽이 안 흔들려요.** 한 파일에 다 몰아두면, 결제 규칙 하나 고치러
> 들어갔다가 재고 규칙까지 같이 읽고 실수로 건드리게 됩니다. 나눠두면 결제 바꿀 땐 결제 문서만,
> 재고 바꿀 땐 재고 문서만 열면 돼요."

> "셋째, **찾기 쉬워요.** 나중에 '재고는 도대체 언제 줄지?' 궁금할 때, `inventory-policy.md` 하나만
> 열면 답이 거기 다 있어야 합니다. 그게 잘 나뉜 신호예요. 반대로 재고 얘기를 결제 문서에서도
> 찾아야 한다면 아직 안 나뉜 겁니다."

**심화 (강사) — 문서를 나누는 건 정리가 아니라 컨텍스트 최적화**
> "방금은 사람 입장에서 봤는데, 사실 이 분리는 에이전트한테도 이득이에요 — **컨텍스트 최적화**죠. 결제 작업을 할 땐 결제
> 문서만 로드하면 되니까, 에이전트가 이번 작업과 무관한 재고 규칙을 안 읽어요 — 노이즈가 줄면
> 정확도가 오르고 토큰 비용도 내려갑니다. 한 파일에 다 몰아두면 모델이 관련 없는 규칙까지 훑느라
> 주의가 분산되고, 정작 이번 변경의 핵심을 놓쳐요. 그래서 **문서 경계를 코드 모듈 경계와 맞추는**
> 겁니다 — 사람이 유지보수하기 좋은 구조가 에이전트한테도 좋은 구조예요."

## E2 실습 — Plan mode로 결제와 재고 책임 나누기 (약 10분)

**실습 2에서 할 일 (소개)**
> "두 번째 실습에서는 **결제 정책과 재고 정책을 각각 다른 문서로 나눕니다.** 같은 흐름을 다뤄서
> 중복되기 쉬우니, 바로 쓰지 않고 `/plan`으로 **책임 경계부터 승인**받은 다음 작성해요. 산출물은
> `docs/payment-policy.md`와 `docs/inventory-policy.md`이고, 작성 뒤엔 세 시나리오(성공·실패·재고
> 부족)를 대입해 두 문서가 안 겹치는지 검증합니다. 여기도 **앱 코드는 안 건드립니다.**"

**1. 바로 작성하지 않고 `/plan`을 쓴다**
> "다음은 결제 정책과 재고 정책을 나눕니다. 두 문서는 같은 사용자 흐름을 다뤄서 중복되기 쉬워요.
> 이번엔 바로 파일을 쓰지 않고 `/plan`으로 **책임 경계부터** 검토하겠습니다. Lab 09에서 구현 계획을
> 깊게 다루지만, 여기선 Plan mode를 **문서 책임 경계를 승인하는 데만** 짧게 씁니다."

Composer에 `/plan` 입력 후:

```
목표: 결제 정책과 재고 정책을 분리해 작성할 접근을 먼저 계획한다.
문맥: @docs/order-policy.md와 @notes/pending-decisions.md @notes/order-status-plan.md를 사용한다.
제약: 파일을 수정하지 말고, 기존 재시도 결정을 장기 정책으로 승격할 근거를 검토한다.
완료 조건: 두 문서의 책임·공유 경계·충돌 검사·작성 후 검증이 구분된다.
```

**2. Plan mode 결과를 검토한다**
기대 구조 — `payment-policy.md`: 결제 성공/실패 판정 · 실패 정보 보존 · 재시도 가능 여부 / `inventory-policy.md`: 재고 검사 시점 · 차감 시점 · 실패 시 미차감 · 음수 재고 방지 / `order-policy.md`와의 경계: 결제 결과가 어떤 상태 전환을 일으키는가.

> "같은 문장이 결제·재고 양쪽에 들어가 있진 않나요? 재고 차감이라는 사건을 두 문서가 서로 다르게
> 정의하진 않나요?"

잘못된 계획이면 좁게 피드백:

```
나머지 계획은 승인한다.
재고 수량의 검사와 변경은 inventory-policy의 책임으로 두고,
payment-policy에는 결제 결과가 재고 정책을 호출하는 조건만 남겨라.
아직 파일은 작성하지 마라.
```


*계획을 항목별로 짚으며 (강사 상세)*
> "지금은 결제 정책과 재고 정책을 바로 작성하지 않고, Plan mode에서 두 문서의 책임을 먼저 나누고
> 있습니다. 여기서 중요한 건 계획이 그럴듯해 보이는지가 아니에요. **기존 결정에 없는 정책을 새로
> 만들지는 않았는지, 같은 원칙을 두 문서에 중복해 넣지는 않았는지**를 사람이 확인해야 합니다."

> "먼저 **결제 정책의 책임** — 어떤 주문이 결제 가능한지, 결제가 성공했는지 실패했는지, 실패했을 때
> 어떤 정보를 남길지를 다룹니다. 실패한 주문의 재결제를 허용할지도 결제 정책의 책임이고, 결제 실패
> API가 402를 반환한다는 응답 기준도 이 문서에 들어갑니다."

> "**재고 정책은 수량 변화만** 책임집니다. 주문을 만들 때 재고가 충분한지 확인하고, 결제가 성공한
> 시점에 차감해요. 결제에 실패하거나 재결제를 거부했을 때 재고를 바꾸지 않는 것도, 재고가 음수가
> 되지 않도록 언제 다시 확인할지도 여기서 정합니다."

> "두 문서는 **'결제 결과'라는 사건을 함께 사용**해요. 결제 정책이 성공·실패를 판정하면, 재고 정책은
> 그 결과에 따라 수량을 바꿀지 결정합니다. 같은 문장을 양쪽에 복사하면 나중에 한 문서만 바뀌면서
> 정책이 충돌할 수 있어요. **각 규칙을 책임지는 문서를 하나만 두고, 다른 문서는 그 결과를 참조**하도록
> 계획해야 합니다."

> "다음은 **재결제 정책**. `pending-decisions.md`에 실패 주문 재결제를 허용하지 않는다고 이미
> 기록돼 있고, `order-status-plan.md`와 앞서 만든 주문 정책도 같은 결정을 씁니다. 이번 단계에서
> 재결제를 다시 고르는 게 아니에요. **이 결정을 현재 작업에만 적용할지, 앞으로도 읽는 장기 결제
> 정책으로 승격할지**를 판단하는 과정입니다."

> "여기서는 **장기 정책으로 승격**하겠습니다. payment_failed 주문에 다시 결제를 요청해도 paid로
> 바뀌지 않아야 하고, 재고도 줄어들면 안 돼요. 이 규칙은 결제 처리·상태 전환·향후 거부 테스트에
> 계속 영향을 줍니다. 여러 작업에서 반복해 지켜야 하니 결제 정책에 남길 근거가 충분합니다."

> "계획이 **기존 범위를 넓히지 않았는지**도 봅니다. 주문 정책엔 refunded의 의미가 있지만 현재
> 구현 범위엔 환불 기능이 없어요 — 상태의 의미를 기록하는 것과 지금 코드를 구현하는 범위는
> 구분해야 합니다. 재결제 거부·재고 부족 응답의 구체적 HTTP 상태나 메시지도 아직 미정이고요.
> **Plan mode가 이 빈칸을 임의로 채웠다면 그 부분은 계획에서 빼야 합니다.**"

> "마지막으로 **작성 후 검증 방법** — 결제 성공을 대입하면 주문은 paid, 재고는 한 번만 줄어야
> 하고, 결제 실패면 주문·실패 정보는 남고 재고는 그대로, 재고 부족 주문은 저장 전에 차단돼야
> 합니다. 두 문서를 처음부터 끝까지 읽고 이 결과가 충돌하지 않는지, `src`·`tests`에 변경이 없는지
> 확인합니다."

> "이제 결제와 재고의 책임 경계가 분명하고, 재결제 금지를 장기 정책으로 승격할 근거도 확인했어요.
> 이 계획을 사람이 승인한 뒤 두 정책 문서 작성을 시작하겠습니다."

**3. 기존 결정을 다시 선택하지 않는다**
> "Lab 05에서 실패 주문 재결제를 허용하지 않기로 이미 정했어요. 여기서 같은 선택지를 다시 주면
> 이전 결정을 무효화하게 됩니다. 지금 판단할 건 재시도 허용 여부가 아니라, **그 작업별 결정을 저장소의
> 장기 정책으로 승격할 만큼 충분한가**예요."
> "이 결정이 이번 결제 실패 개선 요청에만 필요한가요, 아니면 앞으로 모든 결제 상태 변경에서 지켜야
> 할 기준인가요?" → 이번 흐름에서는 **장기 정책으로 승격**한다고 승인.

**4. 계획 승인 후에만 작성한다**

```
책임 경계와 재시도 정책의 승격을 승인한다.
승인된 계획대로 docs/payment-policy.md와 docs/inventory-policy.md를 작성해줘.
각 문서가 책임지는 판단을 중복하지 말고 order-policy의 상태 전환과 충돌하는지도 확인해라.
앱 코드는 수정하지 마라.
```

**5. 작성된 두 문서(payment-policy · inventory-policy)를 리뷰한다**
> "이제 작성된 결제 정책과 재고 정책을 함께 리뷰합니다. **핵심은 문장이 얼마나 자세한지가 아니에요.
> 두 문서가 서로 다른 판단을 책임지는지, 그리고 기존 주문 상태 정책과 충돌하지 않는지**를 확인하는
> 겁니다."

*결제 정책 검토*
> "결제 정책은 **어떤 주문에 결제를 시도할 수 있는지, 성공했는지 실패했는지, 실패 정보를 어떻게
> 보존할지**를 책임집니다. 결제 가능한 상태는 pending으로 제한돼 있고, 성공하고 재고까지 확보되면
> paid로, 실패하면 payment_failed로 전환되며 실패 주문은 삭제하지 않아요."
> "여기서 중요한 게 **실패 정보 보존** — 주문 식별자·실패 금액·처리 시각·실패 사유가 남도록 정의됐는지
> 봅니다. 실패 뒤 주문을 지워버리면 운영자가 추적도, 고객 문의·정산 대응도 못 하니까요."
> "**최초 결제 실패는 HTTP 402 + 실패 정보 반환**이라는 기존 결정이 반영됐는지. 반면 payment_failed
> 주문의 **재결제 요청은 거부**한다는 원칙만 확정이고, 그때 쓸 구체적 HTTP 상태·오류 코드·메시지는
> 아직 미정이에요 — **문서가 이 빈칸을 임의로 채우지 않았는지** 확인합니다. 또 결제 정책은 재고
> 충분 여부를 직접 판단하지 않고, **재고 확인 결과를 받아** 결제 결과와 상태 전환을 결정해야 합니다."

*재고 정책 검토*
> "재고 정책은 **언제 확인하고, 언제 차감하고, 어떤 경우 안 바꾸는지**를 책임집니다. 주문 생성 전에
> 수량을 확인하고, 부족하면 주문을 저장하지 않고 재고도 안 바꿔요. 주문이 정상 생성돼도 **이 시점엔
> 차감하지 않습니다.**"
> "실제 차감은 **결제 시점에 재고를 다시 확인한 뒤**, pending 결제가 성공해 paid로 전환될 때만 **한 번**
> 이뤄져요. 결제 실패·재결제 거부·결제 불가 상태 요청에는 재고를 안 바꾸고, **어떤 경로에서도 재고가
> 음수가 되면 안 된다**는 불변 조건도 명시됐는지 봅니다."
> "재고 부족의 HTTP 상태·오류 메시지도 아직 미정이에요. 그래서 이 문서는 **'재고 부족 판단과 재고
> 변경 여부'까지만** 책임지고 API 응답 형식은 확정하지 않습니다."

*공유 경계 확인*
> "'결제 성공'이라는 사건은 두 정책이 함께 씁니다 — 결제 정책이 성공·실패를 판단하면, 재고 정책이
> 그 결과에 따라 차감 여부를 결정해요. **주문 상태의 의미와 전환 자체는 order-policy.md가 기준**이고,
> 결제·재고 정책이 상태 이름을 새로 정의하거나 다른 전환을 만들면 안 됩니다."

*네 시나리오로 검증* — **[슬라이드: 「네 시나리오로 검증」 표를 띄우고 짚는다]**
- 정상 결제 → 주문 paid, 재고 정확히 한 번 감소
- 결제 실패 → 주문 payment_failed로 남고 실패 정보 보존, 재고 불변
- 재고 부족 → 주문 생성 단계면 저장 안 됨 / 결제 단계면 paid 전환·차감 모두 없음
- 실패 주문 재결제 요청 → 거부, 상태·실패 정보·재고 모두 그대로

> "표를 세로로 읽어 보세요. **주문 상태 열은 payment-policy가, 재고 열은 inventory-policy가** 책임집니다.
> 한 시나리오를 짚으면 두 문서에서 결과가 각각 나오는데, 그게 서로 안 부딪혀야 해요. 예를 들어 결제

**3. 작성한 Task가 아닌 reviewer에게 반박시킨다**
Composer에서 `/review` → `Review uncommitted changes` 또는 custom 범위로 정책 문서만 지정.

```
정책 문서 세 개만 검토해줘.
문서 간 충돌, 판정 불가능한 표현, 민감 정보 노출,
전이표와 관리자 표시 조건의 불일치를 우선순위로 보고해라.
파일은 수정하지 마라.
```

> "`/review`는 같은 Task에게 '잘 썼어?'라고 묻는 것과 달라요. **전담 reviewer가 diff를 읽고 finding을
> 제시하며 작업 트리를 수정하지 않습니다.**"

**4. Review 결과를 사람이 판정한다**
finding을 하나씩 읽기보다 **크게 세 묶음**으로 본다. 핵심은 "지적된 걸 다 고친다"가 아니라
**이미 정한 정책으로 해결되는 지적인지, 새 사람 결정이 필요한 지적인지 가르는 것**.

> "Review에서 네 가지 문제를 찾았습니다. 여기서 중요한 건 지적된 내용을 전부 바로 고치는 게 아니에요.
> Review는 문제를 찾아주는 역할이고, 실제로 어떻게 처리할지는 사람이 결정해야 합니다. 우선 결과를 하나씩
> 읽기보다는 크게 세 묶음으로 보겠습니다."

_묶음 1 — 결제와 재고를 어떤 순서로 처리할지_
> "첫 번째는 결제와 재고를 어떤 순서로 처리할지에 대한 문제입니다. 결제는 성공했는데 그다음에 재고가
> 없다는 걸 알게 되면 어떻게 해야 할까요? 이미 돈이 빠져나갔다면 다시 돌려줘야 할 수도 있어요. 반대로
> 재고부터 줄였는데 결제가 실패하면 줄였던 재고를 복구해야 할 수도 있고요."
> "Review는 지금 정책만으로는 이 순서를 알 수 없다고 지적했습니다. 중요한 문제는 맞아요. 하지만 아직
> 사람이 처리 순서를 정하지 않았습니다. 그러니 여기서 Codex가 알아서 순서를 만들게 하면 안 돼요. 이
> finding은 **보류**하겠습니다. 결제와 재고의 처리 순서는 사람이 따로 정해야 할 질문으로 남깁니다."
> "우선순위가 P1이라고 해서 무조건 바로 수정해야 한다는 뜻은 아니에요. 오히려 영향이 크기 때문에 사람이
> 먼저 결정해야 한다는 뜻으로 볼 수 있습니다."

_묶음 2 — 실패 정보를 어디까지 보여줄 것인가_
> "두 번째는 실패 정보를 어디까지 보여줄 것인가에 대한 문제입니다. 정책에는 실패 정보를 남기고 보여준다고
> 되어 있어요. 그런데 '실패 정보'라고만 쓰면 범위가 너무 넓습니다. 결제 실패 사유는 관리자에게 필요할 수
> 있어요. 하지만 카드 토큰이나 프로그램 내부 오류까지 그대로 보여주면 안 됩니다."
> "여기서는 정보를 세 종류로 나눠 생각하면 쉬워요 — **시스템 내부에만 남길 정보 / 관리자가 업무를 위해 볼
> 정보 / API 응답으로 외부에 보여줄 정보.** 이 세 가지는 같지 않습니다."
> "카드 정보와 내부 오류는 외부에 보여주지 않는다는 원칙은 이미 사람이 정했어요. 이 부분은 Review 의견을
> **수용**하겠습니다. 다만 API가 정확히 어떤 오류 코드와 메시지를 반환할지는 아직 안 정했어요. 그 부분까지
> Codex가 만들어내게 하진 않겠습니다. 따라서 민감 정보를 제외하라는 지적은 수용하고, 구체적인 응답 형식은
> 보류하겠습니다."

_묶음 3 — 실제 입력을 넣어봤을 때 생기는 예외 상황_
> "세 번째는 실제 입력을 넣어봤을 때 생기는 예외 상황이에요. 먼저 같은 상품이 주문에 두 번 들어온 경우.
> 재고가 5개인데 주문에 같은 상품이 3개씩 두 줄 들어왔다고 해보겠습니다. 각 줄만 따로 보면 3개라 재고가
> 충분해 보여요. 하지만 두 줄을 합치면 총 6개라서 실제 재고보다 많습니다."
> "현재 정책이 '각 주문 항목을 검사한다' 정도로만 적혀 있다면, 구현하는 사람이 각 줄을 따로 검사할 수도
> 있어요. 하지만 우리는 이미 재고가 부족한 주문은 막고, 재고가 음수가 되지 않게 하기로 했습니다. 그러므로
> 같은 상품이 여러 줄에 있다면 수량을 먼저 합친 뒤 재고와 비교해야 해요. 이건 새 정책을 만드는 게 아니라,
> 이미 정한 재고 원칙을 정확하게 만드는 일입니다. 이 finding은 **수용**하겠습니다."
> "마지막은 잘못된 요청과 실제 결제 실패를 구분하는 문제예요. 예를 들어 카드 토큰을 아예 보내지 않았다면
> 결제가 실패한 걸까요? 아직 결제를 시도하지도 못한 상태입니다. 요청 형식이 잘못된 거죠. 반면 카드 정보는
> 정상적으로 들어왔고 실제 결제를 시도했지만 거절됐다면 그건 결제 실패예요. 이 둘을 같은 것으로 처리하면
> 안 됩니다. 잘못된 요청은 주문 상태를 바꾸지 않고 결제 실패 기록도 만들지 않아야 하고, 실제 결제를 시도했다
> 실패한 경우에만 주문을 `payment_failed`로 바꾸고 실패 이력을 남겨야 합니다. 이 구분도 기존 정책을 바꾸는
> 게 아니라 뜻을 더 분명하게 만드는 거라 **수용**하겠습니다."

판단 결과를 정리한다.
> "정리해 보겠습니다. 결제와 재고의 처리 순서는 아직 사람의 결정이 필요하므로 **보류**합니다. 카드 정보와
> 내부 오류를 노출하지 말라는 지적은 **수용**합니다. API의 구체적인 오류 코드와 메시지는 아직 정하지
> 않았으므로 **보류**합니다. 같은 상품이 여러 줄에 있으면 수량을 합산해 재고를 검사하도록 **명확히** 합니다.
> 잘못된 요청과 실제 결제 실패를 구분하도록 **명확히** 합니다."
> "여기서 학생들이 가져가야 할 핵심은 하나예요. **Review 결과는 정답지가 아닙니다.** 이미 정한 정책을 더
> 분명하게 만드는 지적은 수용할 수 있어요. 반대로 새로운 정책 결정을 요구하는 지적은 Codex가 채우게 하지
> 않고 사람이 결정할 항목으로 남겨야 합니다."

⚠️ **Review finding은 명령이 아니다.** 사람이 근거를 읽고 반영 여부를 정한다. **수용한 내용만** 원래 작성 Task에 수정 요청하고, **보류한 내용은 해결된 것처럼 쓰지 않았는지 마지막에 확인한다:**

```
나머지 문서는 유지한다.
review finding 중 다음만 수용한다:
- 카드 정보·내부 오류는 외부에 보여줄 정보에 포함하지 않는다
- 같은 상품이 여러 줄에 있으면 수량을 합산해 재고를 검사한다
- 잘못된 요청은 payment_failed로 바꾸지 않고, 실제 결제를 시도했다 실패한 경우만 바꾼다
결제와 재고의 처리 순서, API의 구체적인 오류 코드·메시지는 아직 사람이 정하지 않았으므로
확정된 것처럼 쓰지 말고 '사람 결정 필요'로 남긴다.
해당 부분만 고치고 다른 섹션은 변경하지 마라.
```

> "이제 수용한 내용만 원래 작성 Task에 수정 요청하겠습니다. 보류한 내용은 해결된 것처럼 쓰지 않았는지도
> 마지막에 확인하겠습니다."

## 슬라이드 10 — AGENTS.md는 왜 시키지 않아도 읽히나

정책을 연결하기 **전에**, "먼저 읽는다"가 실제로 어떻게 일어나는지 기제를 연다.

> 시작되면 root `AGENTS.md`가 **컨텍스트에 자동으로 주입**됩니다 — 프롬프트에 안 붙여도요. 하위
> 디렉터리에 AGENTS.md가 또 있으면 **계층으로 병합**되고, 더 가까운 규칙이 우선해요."

> "그다음 Before Editing이 **변경 유형에 따라 어느 정책 문서를 읽을지 라우팅**하고, 필요한 정책만
> 컨텍스트에 올라옵니다. 여기서 중요한 게 — 이 컨텍스트 창은 **예산이 정해져 있어요.** 정책 본문을
> 통째로 AGENTS.md에 넣으면 요청·파일이 쓸 자리를 잡아먹습니다. 그래서 **본문이 아니라 경로만**
> 연결하는 거예요 — AGENTS.md는 백과사전이 아니라 **목차**."

⚠️ **blind 검증의 근거가 여기서 나온다.** — "새 세션으로 확인하는 이유가 이거예요. '이 파일이
실제로 컨텍스트에 주입돼서 라우팅됐는가'를 증명하는 겁니다. 제가 대화로 설명하면 그건 주입이 아니라
그냥 제 말이니까요."

**심화 (강사) — 컨텍스트 창은 에이전트의 유일한 작업 기억**
> "컨텍스트 창은 에이전트의 **유일한 작업 기억**이에요. 세션이 끝나면 사라지고, 다음 세션은 백지에서
> 시작합니다. AGENTS.md 자동 주입은 그 작업 기억에 '턴 0'부터 도메인 사실을 넣어주는 거고요.
> 그런데 여기 함정이 있어요 — **컨텍스트가 길어질수록 모델은 가운데를 덜 봅니다.** 'lost in the
> middle'이라고, 앞·뒤는 잘 보는데 중간은 흘리는 현상이에요. 그래서 정책 본문을 통째로 AGENTS.md에
> 넣으면 정작 중요한 규칙이 중간에 묻혀버립니다. **짧은 라우터 + 필요할 때만 해당 문서 로드**가
> 성능상 유리한 진짜 이유가 이거예요. 실제로 AGENTS.md가 수백 줄 넘어가면 모델이 이번 변경과
> 상관없는 규칙에까지 반응하기 시작합니다."

> 규칙으로 명시**해야 해요. 성향에 맡기면 안 되고, 명시적 정지 조건으로 눌러야 합니다. 이게 있어야

## E4 실습 — CLI 새 대화에서 AGENTS.md routing 증명하기 (약 10분)

**실습 4에서 할 일 (소개)**
> "마지막 실습에서는 지금까지 만든 **세 정책 문서를 `AGENTS.md`에 연결**하고, 그 연결이 실제로
> 작동하는지 증명합니다. 정책 본문을 복사하는 게 아니라 **경로만** 걸고, **이전 대화와 Memory를 끈 CLI
> 새 대화**로 '이 파일들을 스스로 찾아 읽는가'를 blind로 확인해요. 그다음 Lab 07 전체 self-check를 돌려 마무리합니다."

**1. AGENTS.md에는 정책 본문이 아니라 경로를 넣는다**
> "세 정책 문서를 만들었어도 다음 Task가 이 파일들의 존재를 모르면 소용없어요. 그렇다고 정책 본문을
> 전부 `AGENTS.md`에 복사하면 안 됩니다. `AGENTS.md`는 세션 시작 때 **자동으로 컨텍스트에 들어와서**
> 길어질수록 실제 작업에 쓸 컨텍스트 예산을 차지하거든요. 그래서 `AGENTS.md`엔 **변경 유형과 정책
> 경로만** 둡니다."

```
목표: AGENTS.md에 변경 유형별 정책 routing과 정지 조건을 연결한다.
문맥: 세 정책 문서와 현재 AGENTS.md의 Before Editing을 사용한다.
제약: 정책 본문을 복제하지 않고 기존 섹션과 앱 코드를 보존한다.
완료 조건: 주문 상태·결제·재고·관리자 변경이 관련 정책으로 연결되고 누락·충돌 시 편집 전에 멈춘다.
```

diff를 보며:
> "여기엔 '결제 실패 시 무엇을 한다'는 정책 **내용**이 들어가면 안 돼요. '결제 변경 전에는
> `docs/payment-policy.md`를 읽는다'는 **routing만** 있어야 합니다."
`pending-decisions.md`에 Lab 07에서 새로 승인한 결정과 결정일이 기록됐는지도 확인.

**2. Codex CLI에서 이전 대화·Memory를 제외한 새 대화를 만든다**
> "이제 마지막으로 `AGENTS.md`의 routing이 새로운 대화에서도 작동하는지 확인하겠습니다. 지금까지 작업한
> 데스크톱 Task에는 우리가 나눈 대화가 다 남아 있어요. 그래서 여기서 정책 경로를 잘 찾더라도, `AGENTS.md`를
> 읽어서 찾은 건지 앞선 대화를 기억해서 찾은 건지 구분하기 어렵습니다. 그래서 이번 검증은 **Codex CLI로
> 옮겨서** 진행하겠습니다."

먼저 저장소 폴더에서 CLI를 실행한다.
```
codex --enable memories
```
다른 위치에서 실행한다면 저장소 경로를 지정한다.
```
codex --enable memories -C <repo-path>
```
> "여기서 `--enable memories`는 Memory를 쓰겠다는 뜻이라기보단, `/memories` 설정 화면을 쓸 수 있게
> **실험 기능을 켜는** 옵션이에요."

CLI가 열리면 `/memories`로 들어가 **기존 Memory 사용**과 **새 Memory 생성**을 **모두 끈다.**
```
/memories
```
> "기존 Memory를 사용하는 옵션과 새 Memory를 만드는 옵션을 둘 다 끕니다. 이렇게 하면 예전에 저장된
> Memory가 이번 대화에 끼어드는 것도 막고, 이번 대화에서 새 Memory가 만들어지는 것도 막을 수 있어요."

설정을 마치면 새 대화를 시작한다.
```
/new
```
> "이제 새 대화에는 정책 파일의 이름이나 경로를 알려 주지 않겠습니다. 다음 프롬프트만 입력해요."
```
주문 상태와 관련된 코드를 변경하기 전에 읽어야 할 기준과,
작업을 멈추고 사람에게 확인해야 할 조건을 근거 파일과 함께 보고해줘.
파일은 수정하지 마.
```
> "이 프롬프트엔 `AGENTS.md`도, 세 정책 문서의 이름도 안 적혀 있어요. 파일이 저장소에 있다는 것만으로
> 스스로 찾아 읽는지를 보는 겁니다."

**3. Blind 결과를 판정한다**
답변 내용만 보지 말고 **Codex가 실제로 어떤 파일을 읽는지** 확인한다.
> "먼저 root의 `AGENTS.md`를 읽고, 변경 유형에 따라 주문·결제·재고 정책 문서로 이동한다면 routing이
> 작동한 거예요. 결과에서는 크게 두 가지만 봅니다."
> "첫째, **주문 상태 변경 전에 관련 정책을 찾아 읽었는가.** 둘째, 정책이 없거나 서로 충돌하거나 아직
> 결정되지 않은 내용이라면 **코드를 수정하지 않고 사람에게 확인해야 한다고 보고했는가.** 이 두 가지를
> 찾아냈다면 성공입니다. 이전 대화와 Memory를 모두 제외한 상태에서도 저장소 안의 `AGENTS.md`가 다음
> 작업의 출발점 역할을 한 거예요."

통과 기준(체크리스트) — root `AGENTS.md`를 읽었나 · `docs/order-policy.md`를 찾았나 · 결제 변경에 `payment-policy.md`를 연결했나 · 재고 변경에 `inventory-policy.md`를 연결했나 · 누락·충돌·미결이면 편집 전에 멈춘다고 했나 · 파일을 수정하지 않았나.

> "만약 정책 문서를 못 찾았어도 새 대화에 경로를 알려 주면 안 됩니다. 그러면 blind 검증이 깨져요. 대신
> 기존 데스크톱 Task로 돌아가 `AGENTS.md`의 routing만 고친 뒤, CLI에서 다시 `/new`를 실행하고 같은
> 프롬프트로 확인합니다."

⚠️ **이건 모델이 정책 내용을 외웠는지 보는 시험이 아니다.** 새 대화가 저장소에 들어왔을 때 `AGENTS.md`를 출발점으로 삼아 필요한 정책을 스스로 찾고, 결정되지 않은 부분에서 작업을 멈출 수 있는지를 증명하는 절차다.
