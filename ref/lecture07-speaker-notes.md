## 이 강의가 하는 일 (여는 말 전에 강사가 잡고 갈 것)

지금까지(Chapter 1) 우리는 요청 하나를 작업 자산·workflow skeleton으로 바꿨다. 그런데 "주문이
어떤 상태를 거치는지, 결제 실패 때 뭘 남기는지, 재고를 언제 줄이는지" 같은 **도메인 판단은 아직
`notes/`에 작업별로만** 있거나 아예 없다. 7강은 그걸 **여러 작업에서 다시 읽는 `docs/` 정책으로
승격**한다. 그래야 Codex가 매번 추측하지 않고 같은 기준에서 일한다.

**모델·surface 원칙 (전 실습 관통)**
- 긴 판단·문서 작성은 **Desktop**에서. Browser·Computer Use·Scheduled는 안 쓴다.
- **정책은 사람이 정한다.** Codex가 빈칸을 대신 채우지 않는다.
- 충돌·책임 경계 판단 = **Sol** / 승인된 문서 작성 = **Terra** / 형식·경로·diff = **Luna·CLI** /
  자동 적용 확인 = **대화 맥락 없는 새 Task**.
- 각 실습은 **설계 질문 → (Sol 초안) → 사람 승인 → Terra 작성 → Luna 검증** 순서. 승인 전에는
  파일을 쓰지 않는다.

**이 대본에서 강사가 확정해 둔 결정** (Lab README의 `______` 빈칸 — 전부 강사 재량, 필요하면 바꾼다)
- E1 · `paid` 이후 취소: **환불(`refunded`)로만 처리**한다 → `paid→cancelled`는 금지, `paid→refunded` 허용.
- E2 · 재시도: **이번 정책에서는 보류**(허용하지 않음). 실패는 `payment_failed`로 보존하고 재결제는 새 주문으로.
- E3 · 제외 정보: 카드번호·카드 토큰·내부 예외.

> 체크포인트가 하나 늘어나요** — 규칙을 잘 적어두면 나중에 확인이 쉬워집니다. 직접 해보죠."

### Human Gate — 상태 구조 승인

⚠️ **표가 나왔다고 바로 파일 X. 구조가 토대라 여기서 사람이 승인한다.**

확인할 것 — 결제 전·성공·실패·취소·환불이 서로 다른 상태로 설명되나 · `payment_failed`·`cancelled`·
`refunded`를 종료 상태로 명시했나 · **paid 이후 취소를 허용할지 환불로만 갈지 사람이 골랐나** ·
이번에 제외한 상태를 마치 구현된 것처럼 쓰지 않았나.

> "여기서 제가 결정을 박습니다 — **paid 이후는 환불로만.** 이제 이 승인된 내용만 Terra한테
> 파일로 옮기라고 하고, 없던 상태나 전환을 몰래 추가하지 않았는지 Luna로 diff를 봅니다."

승인 후: Terra에게 승인 내용만 `## 상태 정의`·`## 전환 조건`에 기록 → `git diff -- docs/order-policy.md`.

**검증**: 상태 5개 의미·진입 조건 / 전환표 시작·이벤트·종료 / 허용·금지·보류 전환 구분 / 승인 전
선택이 정책으로 굳지 않음 / diff는 order-policy.md만.

## 슬라이드 07 — 결제 실패 주문을 지우면 무엇이 사라지나 (클립 1 마무리)

E1으로 상태·전환을 정했으니, 왜 `payment_failed`가 '취향'이 아니라 '필연'인지 못 박고 클립을 닫는다.
> "지금 v0는 결제가 실패하면 주문을 **그냥 지웁니다.** 그럼 뭐가 사라지냐 — 왼쪽이에요. 실패 사유가
> 안 남으니 **감사 추적이 끊기고**, 재시도하면 같은 주문이 아니라 **새 주문이 또 생겨 멱등성이
> 깨지고**, 실패 건이 집계에서 빠져 **관리자 정산이 안 됩니다.** 게다가 한 번 지우면 코드로 못
> 되살려요."

> "오른쪽 — `payment_failed`로 **상태만 바꿔** 남기면 이력도 남고, 재시도도 안전하고, 정산도 됩니다.
> 그래서 실패를 상태로 남기는 건 취향이 아니라 **기술적 필연**이에요. 이게 다음 클립의 결제·재고

# 클립 2 — 결제/재고 원칙 (약 10분)

## 슬라이드 08 — 결제/재고 원칙

> "정본 규칙 세 줄이에요. 결제가 성공하면 그때 재고를 줄인다. 실패하면 재고를 건드리지 않는다.
> 재고가 부족하면 주문을 만들기 전에 막는다. **재고는 결제가 성공한 뒤에만 줄어든다** — 이게 핵심이고,
> v0는 지금 이걸 안 지켜요(음수 재고까지 허용). 오늘 문서로 못 박습니다."

## 슬라이드 09 — 결제와 재고는 다른 판단

> "그런데 왜 파일을 둘로 나눌까요? 결제 판단이랑 재고 판단은 **다른 질문에 답하거든요.** 왼쪽
> payment은 '성공·실패를 어떻게 판단하고 실패하면 뭘 남기나', 오른쪽 inventory는 '언제 줄이고
> 부족하면 어디서 막나'. 한 파일에 몰아두면 결제 규칙 하나 고칠 때 재고까지 흔들려요. **책임을
> 나눠 둡니다.**"

## E2 실습 — 결제 원칙과 재고 원칙 분리 (Desktop)

**산출물**: `docs/payment-policy.md`(`## 결제 원칙`) + `docs/inventory-policy.md`(`## 재고 원칙`)

**설계 질문 (강사가 답하며)**
> "결제 실패 때 뭘 보존하나 — 상태·금액·시각·실패 사유. 성공·실패·재시도를 뭘로 판정하나.
> 재고는 언제 검사·차감하나. 부족·음수 재고를 어떤 조건으로 막나. 그리고 **재시도** — 이건 제가
> 정합니다. 오늘은 **재시도를 허용하지 않아요.** 실패는 payment_failed로 남기고, 다시 결제하려면
> 새 주문으로. 재시도 로직은 이번 정책 범위 밖입니다."

**Codex 작업 중 설명** — Sol에게 E1 전환표와 대조해 두 원칙 초안을 **분리**해서 그리게 한다.
> "Sol한테 E1에서 만든 주문 전환표랑 pending-decisions를 대조해서, 결제 초안이랑 재고 초안을
> **따로** 그려달라고 합니다. 결제 문서는 승인·실패·재시도·실패 정보 보존, 재고 문서는 검사·차감·
> 미차감·부족 차단. 아직 파일은 안 써요."

첫 프롬프트:

```
목표: 결제 원칙과 재고 원칙을 서로 다른 두 정책 문서로 작성한다.
문맥: @docs/order-policy.md와 Lab 05·06의 결정·계획 기록을 사용한다.
제약: 재시도 허용 정책은 사람이 확정하며, 두 문서에 같은 원칙을 복제하거나 코드를 수정하지 않는다.
완료 조건: 성공·실패·재시도와 재고 검사·변경·부족 차단을 각각 판정할 수 있다.
```

### Human Gate — 결제와 재고 경계

사람이 확인: 결제 성공 후 재고 반영 · 실패 시 재고 미반영 · 재고 부족 주문의 저장 전 차단 · 음수
재고 금지 · 실패 정보 보존 범위. **재시도 허용 여부는 코드에서 추론하지 말고 사람이 최종 승인**
