Part 1 · Chapter 1 · 6강 · 실습 · 약 55분 · **슬라이드 없음** — notes 문서와 Codex를 split 화면으로

## 이 노트 쓰는 법

- 5강과 같은 방식이다. 왼쪽에 lab README·notes 문서, 오른쪽에 Codex. `[@파일]`은 mention, `[…]`는
  화면 조작이다. 인용부호 안은 그대로 읽어도 되는 말이다. ⚠️는 놓치면 뒤가 어긋나는 지점.
- 산출물은 `notes/small-development-workflow.md` 하나다. 기존 문서를 합치지 않고 **연결**한다.

# E1 — Chapter 1 문서 세트를 하나의 handoff로 묶기 (약 15~20분)

지금까지 하나의 요청을 여러 문서로 나눠 처리했다 — 요청·초기 사실, 사람이 결정할 질문, Human
Gate·멈춤 조건, repo 규칙, 현재 동작·수정 범위, 검증 계획. **E1은 이걸 다시 합치지 않는다.** 다음
작업자가 하나의 진입 문서에서 필요한 기준 문서를 찾아가게 연결하고, **맥락 없는 새 Task에서 실제로
이어받을 수 있는지** 검증한다.

모델: 문서 감사 Sol · 결정 반영 Terra · 진입 문서 작성 Terra · cold-start 검증 Terra(일부러 약한
모델) · 최종 확인 Luna.

시작 상태: `order-status-plan.md`에 관련 파일·현재 동작·수정/제외 범위·검증 계획이 있고, Human
Gate 정책 결정은 이미 내렸다. `small-development-workflow.md`는 아직 없다. src·tests 무변경.

## 여는 말

> "지금까지 요청 하나를 여러 문서로 나눠 처리했죠. 요청 원문은 `order-status-request.md`, 사람이
> 답할 질문은 `pending-decisions.md`, Human Gate와 멈춤 조건은 `task-boundary.md`, 최종 수정 범위와
> 검증 계획은 `order-status-plan.md`."

> "근데 **문서가 여러 개 있다고 해서 handoff가 되는 건 아니에요.** 다음 사람이 뭘 먼저 읽어야 하는지,
> 서로 다른 내용이 있으면 뭘 기준으로 삼아야 하는지 알아야죠. 오늘은 문서를 합치지 않고, 각 문서의
> 역할과 우선순위를 연결합니다. 마지막엔 **맥락 없는 새 Task에서 진짜 인수인계가 되는지** 확인해요."

## 1. 문서 역할·충돌 감사 (Sol)

먼저 고치지 않는다. 각 문서가 무엇의 기준인지, 오래된 상태나 충돌이 있는지만 조사시킨다.

`[@order-status-request.md @pending-decisions.md @task-boundary.md @order-status-plan.md 연결]`
(AGENTS.md는 자동 로드 — 결과에서 repo 공통 규칙과 요청별 결정이 구분되는지 본다)

```
목표: Chapter 1 산출물을 다음 작업자가 이어받을 수 있는 하나의 문서 세트로 정리하기 전에 역할·중복·충돌을 점검한다.
문맥: @notes/order-status-request.md @notes/pending-decisions.md @notes/task-boundary.md @notes/order-status-plan.md와 자동 적용된 AGENTS.md를 사용한다.
제약: 내용을 합치거나 새 정책을 결정하지 않는다. 각 문서가 무엇의 기준인지, 다른 문서와 겹치거나 상태가 어긋난 부분만 확인하고 파일은 수정하지 않는다.
완료 조건: 문서별 역할·기준 정보·읽는 순서·다른 문서와의 연결과, 다음 작업자를 막을 충돌·누락을 채팅에 제시한다.
```

> "이건 파일 요약이 목적이 아니에요. **각 문서의 역할**을 봅니다 — 요청 원문은 어느 문서가 기준인지,
> 사람 결정은 어디서 추적하는지, 최신 수정 범위는 어느 문서를 따라야 하는지. 그리고 문서마다 만든
> 시간이 다르니까 초기 추정과 최종 계획이 다를 수 있어요. **모든 차이가 오류는 아닙니다** — 정상적인
> 시간 차이랑 진짜 충돌을 갈라야 해요."

## 2. 감사 Human Gate — 정상 시간차 vs 실제 충돌

⚠️ **Codex가 충돌을 찾았다고 다 고치지 않는다. 여기서 강사가 갈라 준다.**

| 실제로 고쳐야 하는 것 (충돌) | 그대로 두는 것 (정상 시간차) |
| --- | --- |
| 이미 결정된 질문이 `pending-decisions`에 미결로 남음 | `order-status-request`의 초기 추정 ≠ 최종 plan |
| `task-boundary` Gate가 통과 여부를 안 보여줌 | plan 안에 초기 조사와 최종 범위가 함께 있음 |
| 결정 결과 ≠ plan의 수정/제외 범위 | `AGENTS.md`에 이 요청의 구체 정책이 없음 |
| 테스트 범위 결정 ≠ 실제 검증 계획 | |

> "요청 문서의 `## 추정`은 요청을 처음 정리할 때의 가설이에요. 최신 plan과 다르다고 덮어쓰지
> 않습니다. **반면** `pending-decisions`가 이미 답한 질문을 계속 미결로 보여주면, 다음 사람을 잘못
> 멈추게 하니까 이건 고쳐야 해요. `task-boundary`는 Gate 질문·금지 조건은 그대로 두고, **통과
> 상태와 결정·계획 링크만** 더합니다."

## 3. 결정 상태와 Human Gate 기록 최신화 (Terra)

⚠️ **진입 문서를 만들기 전에 이걸 먼저 한다.** 감사에서 드러났듯, 이미 사람이 답한 결정이
`pending-decisions.md`엔 아직 미결로, `task-boundary.md` Gate는 승인 전 상태로만 보인다. 이대로
진입 문서를 만들면 **오래된 상태를 그대로 연결**하게 되고, 다음 작업자가 이미 끝난 결정을 다시 묻는다.
그래서 기존 문서의 현재 상태부터 맞춘 뒤 묶는다.

**여기서 새 정책을 결정하지 않는다.** 5강에서 이미 내린 결정을 문서에 반영만 한다. 손대는 파일은
`pending-decisions.md`·`task-boundary.md` **둘뿐** — request·plan·AGENTS·src·tests는 안 건드린다.

### 사람이 정합 수정 범위 승인

감사 결과를 보고 강사가 먼저 확정한다:

> "감사 결과 기준으로 정합 수정 범위를 승인할게요. `pending-decisions.md`는 **삭제 안 합니다** —
> 2강에서 질문을 발견하고 5강에서 답한 과정을 보여주는 **결정 추적 문서**로 씁니다. 기존 질문·선택지는
> 그대로 두고, 실제 선택 결과랑 plan 적용 위치만 더해요."

> "재고 부족 차단이나 관리자 실패 사유처럼 **기존 질문에 없던 E3 추가 결정**은 원래 선택지에 섞지
> 말고 별도 구역으로 뺍니다. 테스트 범위는 현재 plan의 실제 검증 계획과 맞추고요."

> "`task-boundary.md`엔 **정책 답을 다시 안 적습니다.** Gate가 통과됐다는 상태와 결정·계획 문서 링크만
> 더해요."

### 계약

```
목표: Lab 05에서 이미 내린 사람 결정을 Chapter 1 문서 세트에 반영한다.
문맥: @notes/pending-decisions.md @notes/task-boundary.md @notes/order-status-plan.md와 방금 사람이 승인한 정합 수정 범위를 사용한다.
제약: 새로운 결정을 만들지 않는다. pending-decisions.md의 기존 질문·선택지는 보존하고 각 질문의 처리 상태·실제 선택 결과·plan 적용 위치를 기록한다. 기존 선택지에 없던 E3 추가 결정은 별도 구역으로 분리한다. task-boundary.md에는 각 Human Gate의 통과 상태와 결정·계획 문서 링크만 추가하고 기존 질문과 승인 전 금지 조건은 보존한다. 다른 파일은 수정하지 않는다.
완료 조건: 모든 결정 상태가 현재 order-status-plan.md와 일치하고, E3 추가 결정이 기존 질문의 선택 결과와 구분되며, 두 Human Gate가 통과 상태로 표시돼 있다.
```

⚠️ **Codex 도는 동안 — pending과 보류를 구분하라고 짚는다.**

> "이건 정책 결정이 아니라 이미 내린 결정을 상태에 반영하는 작업이에요. 특히 **pending이랑 보류를
> 구분**해야 합니다. pending은 아직 답이 없어서 다음으로 못 가는 상태고, 보류는 사람이 **이번엔 안
> 하기로 결정한** 상태예요. Lab 05 범위가 확정됐으면, 이번 작업을 막는 미결 질문은 없어야 합니다."

### 결과 확인

**pending-decisions.md** — 제목·도입이 현재 역할을 설명하나 (`## 결정 추적` — 사람이 검토한 질문과
처리 상태를 추적) · 기존 질문·선택지 보존됐나 · 질문마다 처리 상태·실제 선택 결과·plan 적용 위치가
있나 · **확정과 이번 작업 보류가 구분됐나** · 실제 선택 결과가 plan과 일치하나 · 관리자 실패 정보의
원래 선택과 **실패 사유 추가**가 분리됐나 · 재고 부족 **생성 전 차단**이 `## E3에서 추가로 확정한 결정`
구역에 있나.

**task-boundary.md** — Gate 1·2에 `통과 상태: 통과` + 결정 문서(pending-decisions)·계획 문서(plan)
링크가 붙었나 · 기존 질문·승인 전 금지 조건 보존됐나 · 결정 내용을 Gate에 다시 복사하지 않았나.

> "Gate가 통과됐다고 승인 전 금지 조건을 지우지 않아요. 이건 지금 다음 작업을 막는 규칙이 아니라,
> **당시 왜 사람이 필요했고 승인 전엔 뭘 하면 안 됐는지 보여주는 작업 이력**이에요. 거기에 통과
> 여부랑 결정 문서 위치만 더하는 겁니다."

### 리허설 피드백 — 테스트 범위가 어긋난 경우

"실제 선택 결과: 완료 조건의 네 흐름만 검증"으로 나올 수 있는데, 현재 plan은 더 넓은 범위를 쓴다.
기존 두 번째 선택지("실패 주문 조회·재고 유지·관리자 조회·재결제·중복 차감 방지 모두")를 plan에 맞게
「관리자 조회」→「관리자 실패 사유 조회」로 명확히 하고 그걸 실제 결과로 삼는다:

```
테스트 범위만 현재 order-status-plan.md와 맞게 고쳐줘.
두 번째 선택지의 "관리자 조회"를 "관리자 실패 사유 조회"로 명확히 바꾸고,
실제 선택 결과는 수정된 두 번째 선택지로 기록해라.
기존 선택지는 이력으로 보존하고, 다른 내용과 파일은 수정하지 마라.
```

수정 후 실제 결과 — 실패 주문 조회 · 재고 유지 · **관리자 실패 사유 조회** · 재결제 · 중복 차감 방지.

### 정합 검증 (Luna)

기록 후 파일은 안 고치고 검토만:

```
방금 수정한 문서 정합을 검토해줘.
pending-decisions.md의 모든 결정 상태와 실제 선택 결과가
order-status-plan.md의 수정·제외 범위와 테스트·검증 계획에 일치하는지 확인해라.
task-boundary.md의 Human Gate 1·2가 통과 상태인지, 기존 질문과 승인 전 금지 조건이 보존됐는지 확인해라.
새 정책이 추가됐거나 요청·계획 내용이 중복 복사됐는지도 확인해라.
문제가 없다면 파일은 수정하지 말고 결과만 보고해줘.
```

변경 범위: `git diff -- notes/pending-decisions.md notes/task-boundary.md` — **두 파일만** 바뀌고
질문·선택지가 보존됐는지, 예상 못한 정책이 안 붙었는지 본다. `git diff --stat -- src/ tests/` 는
출력이 없어야 한다. (order-status-plan.md도 안 바뀌어야 한다.)

## 4. Workflow 진입 문서 만들기 (Terra)

이제 문서 상태가 일치한다. 다음 작업자가 모든 문서를 직접 찾지 않게 `small-development-workflow.md`를
진입점으로 만든다. **상세 내용은 복사하지 않고, 역할·읽는 순서·현재 상태·다음 작업만 연결한다.**

```
목표: 승인한 Chapter 1 문서 관계를 다음 작업자의 진입점인 notes/small-development-workflow.md로 정리한다.
문맥: @notes/order-status-request.md @notes/pending-decisions.md @notes/task-boundary.md @notes/order-status-plan.md와 자동 적용된 AGENTS.md를 사용한다.
제약: 요청·결정·계획의 상세 내용을 복제하지 않고 기준 문서에 연결한다. E2의 재사용 가능한 workflow template과 E3의 Codex surface 배정은 아직 작성하지 않는다. 새 정책을 추가하거나 src/와 tests/를 수정하지 않는다.
완료 조건: 진입 문서에서 현재 작업, 문서 세트와 역할, 읽는 순서, 현재 멈춘 지점, 다음 작업, 아직 하지 않을 일을 찾을 수 있다.
```

기대 구조 — `# Small Development Workflow` 아래: `## 현재 작업` · `## 문서 세트와 역할` · `## 읽는
순서` · `## 현재 멈춘 지점` · `## 다음 작업` · `## 아직 하지 않을 일`.

> "이건 새 계획 문서가 아니에요. 요청은 요청 문서에, 결정은 결정 문서에, 범위·검증은 plan에 그대로
> 둡니다. 이 파일은 **어떤 문서를 어떤 순서로 읽어야 하는지 알려주는 안내판**일 뿐이에요."

확인 — 현재 작업이 한 문단에서 잡히나 · 문서 역할이 구분됐나 · 요청/결정/계획 기준 문서가 명확한가 ·
읽는 순서가 있나 · Gate 통과·구현 미착수가 표시됐나 · 다음 작업이 뭔지 알 수 있나 · E2 template·E3
surface가 미리 안 들어갔나 · 상세가 중복 복사 안 됐나.

## 5. 새 Task에서 cold-start handoff 검증 (Terra · 일부러 약한 모델)

⚠️ **핵심 증거다. 4·5강의 「새 세션 블라인드 검증」이 이제 문서 세트 전체로 확장된다.**

지금 Task는 앞선 대화를 다 안다 — 문서가 부족해도 기억으로 답한다. 그래서 **맥락 없는 새 Task**를
열고 진입 문서 하나만 준다.

`[Codex Desktop에서 새 Task → @notes/small-development-workflow.md만 연결 → 다른 문서는 mention 안 함]`

```
@notes/small-development-workflow.md를 진입점으로 삼아
이 문서가 연결한 작업 자료를 필요한 순서대로 읽어줘.
파일은 수정하지 말고 다음 작업자가 이어받는다는 관점에서
현재 요청, 확인된 현재 동작, 사람의 확정·보류 결정,
수정·제외 범위, 검증 계획, 현재 멈춘 지점,
바로 다음 작업, 지금 하면 안 되는 일을 보고해줘.
문서만으로 확인할 수 없는 내용은 추측하지 말고 누락으로 표시해줘.
```

> "이 Task엔 이전 대화가 없어요. 그러니 요청·결정·계획을 제대로 설명하면 **문서 연결이 실제로
> 작동한 겁니다.** 반대로 이미 결정한 걸 다시 묻거나 바로 구현하려 하면, 진입 문서에 상태나 다음
> 작업이 부족한 거예요."

**성공 판정** — 새 Task가 이걸 회수하면 성공: `payment_failed` 추가·`refunded` 보류 · 실패 응답 402 ·
실패 주문 보존·재결제 불허 · 재고 부족 생성 전 차단 · 관리자 실패 사유 · 여섯 검증 시나리오 · 검증
명령 순서 · Gate 통과 · 구현 미착수 · **응답 메시지·필드 규칙은 추측하면 안 된다는 점**.

## 6. 리허설 피드백 — 다음 작업을 구현으로 오해한 경우

리허설에서 "승인된 수정 범위 안에서 구현 단계로 진행합니다"로 나올 수 있다. 하지만 Lab 06의 바로
다음은 구현이 아니라 **E2 workflow skeleton 작성**이다.

⚠️ **handoff 실패 전체가 아니다.** 요청·결정·계획은 다 이해했고, 진입 문서의 `## 다음 작업` 표현만
모호한 것이다. 전체를 다시 쓰지 말고 그 섹션만 최소 보완한다 (원래 Task로 돌아가서):

```
cold-start handoff 결과에서 바로 다음 작업이 구현으로 잘못 해석됐다.
notes/small-development-workflow.md의 ## 다음 작업만 수정해줘.
바로 다음 작업은 현재 문서 세트에서 공통 구조를 추출해
docs/templates/workflow-skeleton.md를 만드는 E2임을 명확히 해라.
그다음은 Codex surface 연결이며,
order-status-plan.md는 이후 구현의 입력이지만
Chapter 1에서는 구현과 src/, tests/ 변경을 시작하지 않는다고 적어라.
다른 섹션과 파일은 수정하지 마라.
```

## 7. handoff 재확인 + 최종 검증 (Luna)

새 Task에서 진입 문서를 다시 읽게 한다:

```
@notes/small-development-workflow.md를 다시 읽고
현재 바로 다음 작업과 아직 시작하면 안 되는 작업만 보고해줘. 파일은 수정하지 마라.
```

통과: 바로 다음 = 재사용 가능한 workflow skeleton 작성 / 그다음 = Codex surface 연결 / 아직 안 할 것 =
주문 상태 구현과 src·tests 변경.

최종 체크 — pending-decisions에서 질문·최종 결정 추적 가능 · E3 추가 결정이 기존 선택지와 분리 ·
task-boundary Gate 1·2 통과 · `small-development-workflow.md` 존재 · 기준 문서 구분 · 중복 복사 없음 ·
새 Task가 진입 문서 하나로 상태 설명 · 다음 작업을 skeleton 작성으로 인식 · E2/E3 미작성 · src·tests
무변경(`git diff --stat -- src/ tests/` 출력 없음).

## E1 마무리

> "이번 실습에서 문서를 하나로 합치지 않았어요. 요청은 요청 문서에, 결정은 결정 추적 문서에, Gate는
> 경계 문서에, 범위·검증은 plan에 그대로 뒀죠. 대신 `small-development-workflow.md`를 진입점으로 만들어
> **역할과 읽는 순서를 연결**했습니다."

> "그리고 새 Task에 이 문서 하나만 줘서, 이전 대화 없이도 현재 요청·결정·계획·다음 작업을 복원할 수
> 있는지 확인했어요. 그 과정에서 다음 작업을 구현으로 오해하는 것도 잡았는데, 전체를 다시 쓰지 않고
> **원인이 있는 `## 다음 작업` 연결만** 최소 보완했고요."

> "이제 구체적인 작업 세트 하나가 만들어졌습니다. 다음 E2에서는 여기서 **공통 구조를 뽑아**, 다른
> 요청에도 쓸 수 있는 빈 workflow skeleton으로 바꿉니다."

# E2 — Workflow skeleton 만들기 (약 20분)

E1은 특정 사례의 문서를 연결했다. E2는 그 사례에서 **반복 가능한 구조만 뽑아**, 다음 요청에도 쓸
수 있는 **빈** workflow template을 만든다. 핵심은 원샷으로 템플릿을 쓰게 하는 게 아니다 — 다섯
단계다: ① 실제 문서에서 섹션 책임 추출 → ② 사람이 경계 승인 → ③ Codex가 빈 템플릿 작성 →
④ 독립 subagent가 처음 보는 문서처럼 리뷰 → ⑤ 사람이 필요한 리뷰만 반영. 실습은 세 단계로
진행하고, 마지막 검증은 종료 확인으로 처리한다.

모델: 섹션 경계 설계 Sol · 템플릿 작성 Terra · 독립 리뷰 Sol(별도 subagent) · 반영 Terra · 종료 확인 Luna.

## 여는 말 · 시작 상태

`[git status --short 로 현재 변경 확인]`

> "먼저 현재 변경 파일을 봅니다. E1에서 바꾼 notes 파일이 보일 거예요 — 이건 E2에서 새로 바꾼 게
> 아닙니다. **지금 상태를 기준선으로** 기억해 두고, E2에선 `docs/templates/workflow-skeleton.md`만
> 새로 만듭니다."

이번 단계 — 하는 것: 실제 문서에서 반복 가능한 8개 섹션의 책임을 추출해 빈 템플릿으로 / 안 하는
것: 주문 상태 내용 복사·새 정책·E3 surface·구현 / 산출물: `docs/templates/workflow-skeleton.md`
(`docs/`는 여기서 처음 생긴다).

## 1단계 — 8개 섹션의 책임 경계 설계 (Sol)

바로 파일을 안 쓴다. 먼저 현재 사례로 각 섹션이 무슨 정보를 책임지는지 정한다. **제목만 여덟 개
만들면 정보가 쉽게 중복**되기 때문이다 — 예: `현재 파악`↔`현재 동작`, `관련 맥락`↔`결정 필요 사항`,
`검증 기준`↔`다음 단계`.

`[@notes/small-development-workflow.md @labs/CONVENTIONS.md 연결]` (진입 문서가 나머지 기준 문서를
이미 연결하므로 요청·결정·계획을 다시 mention하지 않는다 — E1 산출물을 실제로 써 보는 자리다)

```
목표: E1 문서 세트를 사례로 삼아 재사용 가능한 workflow skeleton의 8개 섹션별 책임 경계를 설계한다.
문맥: @notes/small-development-workflow.md와 그 문서가 연결하는 기준 문서, @labs/CONVENTIONS.md를 사용한다.
제약: 아직 템플릿 파일을 작성하지 않는다. 주문 상태 작업의 내용을 답으로 복사하지 않고, 요청 원문·현재 파악·관련 맥락·현재 동작·결정 필요 사항·수정 계획·검증 기준·다음 단계의 이름은 유지한다.
완료 조건: 각 섹션의 목적·입력 근거·작성 질문·남겨야 할 결과·이웃 섹션과의 구분이 표로 정리돼 있다.
```

> "지금 Codex는 문서를 요약하는 게 아니라, **문서 사이에서 정보가 이동한 방식**을 뽑고 있어요.
> 주문 상태 요청은 사례일 뿐이고, 결과는 다른 요청에도 써야 합니다. 그러니 결과에 `payment_failed`,
> 재고 차감, 관리자 조회 같은 **답이 들어가면 안 돼요.**"

예상 — 섹션 / 목적 / 입력 근거 / 작성 질문 / 남겨야 할 결과 / 이웃 섹션과의 구분, 6열 표.

### Human Gate 1 — 섹션 책임 승인 (사람)

⚠️ **표가 나왔다고 바로 파일 안 만든다. 구조가 틀린 채 템플릿을 만들면 8섹션을 다 고쳐야 한다 —
지금이 되돌리기 제일 싼 시점이라 경계만 확인한다.**

확인 — `요청 원문`은 사용자 표현·완료 조건을 해석 없이 보존하나 · `현재 파악`은 이해·조사 범위·남은
공백을 다루나 · 흐름별 실제 행동은 `현재 동작`에만 남나 · `결정 필요 사항`은 결정의 상태·결과를
추적하나(미결 질문만 두는 곳이 아님) · 미결 결정이 `수정 계획`으로 안 넘어가나 · `검증 기준`은 계획과
실행 결과를 구분하나 · `다음 단계`에 멈춘 지점·아직 안 할 일이 남나.

리허설에서 자주 나온 것 — `요청 원문`↔`현재 파악` 설명 뒤바뀜, `현재 파악`↔`현재 동작` 조사 사실
중복, `결정 필요 사항`을 미결 질문만 두는 곳으로 제한, 검증 계획↔실행 상태 구분 부족. 같은 경계
문제가 보이면 **강사가 실제로 입력하는 피드백**은 이 문구 그대로:

```
섹션 구조와 나머지 책임 경계는 승인한다.
다음 네 부분만 고쳐 다시 표를 보여줘. 아직 파일은 작성하지 마라.

- 요청 원문은 해석하지 않은 출처를 보존하고, 현재 파악은 요청에 대한 이해·확인 범위·남은 공백을 정리하도록 구분한다.
- 현재 파악에는 흐름별 코드 동작을 반복하지 말고, 실제 사용자 흐름은 현재 동작에만 둔다.
- 결정 필요 사항은 미결 질문만 두는 곳이 아니라 이번 요청에서 생긴 질문의 미결·확정·보류 상태와 계획 반영 위치를 추적하도록 한다.
- 검증 기준에는 계획한 검증과 실제 실행 결과를 구분할 수 있는 질문을 추가한다.

8개 섹션의 이름과 순서는 유지해라.
```

> "전체를 다시 만들게 하지 않고, **제가 찾은 네 가지 경계만** 고치게 합니다. 나머지 구조는 승인한다고
> 먼저 밝혀서 정상인 부분까지 다시 쓰지 않게 하고요. 그리고 「아직 파일은 작성하지 마라」 — **구조가
> 승인되기 전에 산출물이 생기는 걸 막습니다.**"

문제가 항상 다 나오는 건 아니다. 이미 기준을 충족하면 불필요한 피드백을 붙이지 않는다. 통과하면:

```
이 섹션 책임 경계를 승인한다.
이제 이 경계를 유지한 빈 workflow template을 작성해줘.
```

## 2단계 — 빈 Workflow Template 작성 (Terra)

템플릿은 답안지가 아니라, 작업자가 **각 단계에서 뭘 확인하고 언제 다음으로 넘어가는지** 알려주는
구조물이다. 재사용하니까 `notes/`가 아니라 `docs/templates/`에 둔다.

```
목표: 승인한 8개 섹션 책임 경계를 재사용 가능한 workflow skeleton으로 작성한다.
문맥: 방금 승인한 섹션 계약과 @labs/CONVENTIONS.md를 사용한다.
제약: docs/templates/workflow-skeleton.md만 생성한다. 특정 주문·결제·재고 정책이나 완성된 답을 넣지 않는다. 각 섹션에는 목적·작성 질문·완료 판정이 있어야 하며 E3의 Codex surface는 배정하지 않는다.
완료 조건: 정확히 8개 workflow 섹션이 있고, 모든 섹션이 빈 상태에서도 무엇을 확인하고 언제 완료되는지 알려준다.
```

여덟 섹션: 요청 원문 · 현재 파악 · 관련 맥락 · 현재 동작 · 결정 필요 사항 · 수정 계획 · 검증 기준 ·
다음 단계. 각 섹션은 **목적 / 작성할 때 확인할 질문 / 다음으로 넘어가는 완료 판정** — 구체적 답·예시는
넣지 않는다.

> "diff만 보지 말고 **렌더된 Markdown으로 읽어** 봅니다. 재사용 템플릿은 구조가 일정해야 정보를 빨리
> 찾아요. 섹션마다 목적·질문·완료 판정이 같은 패턴으로 보이는지."

빠른 확인 — 여덟 섹션이 같은 계층인가 · 한 섹션만 과하게 길지 않나 · 질문이 답을 미리 고르고 있지
않나 · 주문·결제·재고 같은 사례 내용이 남지 않았나 · E3 surface(Desktop·CLI·Browser·Automation)가
안 들어갔나 · 다른 파일을 같이 안 고쳤나. 명백한 구조 오류가 없으면 문장을 계속 다듬지 말고 독립
리뷰로 넘어간다.

## 3단계 — Subagent 독립 리뷰 + 선택 반영 (Sol · 별도 subagent)

⚠️ **주 Task는 자기가 의도한 구조를 이미 안다. 같은 Task에 「검토해줘」 하면 작성 당시 맥락으로 빈
부분을 자연스럽게 메워 읽는다.** 그래서 별도 reviewer subagent에게 템플릿만 독립적으로 검토시킨다.
(4강 새 세션·6강 E1 cold-start와 같은 원리 — 검증은 만든 사람이 아니라 바깥에서.)

```
목표: reviewer subagent 하나를 사용해 @docs/templates/workflow-skeleton.md를 처음 받는 작업자의 관점에서 독립 검토한다.
문맥: 작성된 workflow skeleton만 검토 대상으로 사용한다.
제약: reviewer는 파일을 수정하지 않는다. 사실과 가설 혼동·결정 전 계획 확정·섹션 중복이나 공백·검증 상태 오인·handoff 실패·특정 사례 종속만 확인하고, 문제가 없는 항목을 억지로 만들지 않는다.
완료 조건: 실제 수정 필요 가능성이 있는 문제마다 관련 섹션·다음 작업자에게 미치는 영향·최소 수정 제안이 보고돼 있다.
```

리허설에선 한 건 — `현재 파악`의 「요청 이해」가 확인된 사실처럼 쓰일 가능성(→ 다음 결정이 미확인
해석을 근거로 삼을 수 있음, 사실/해석 구분 완료 판정 추가 제안). 나머지는 통과(수정 계획은 확정 결정만,
검증 기준은 상태 구분, 다음 단계는 멈춘 지점 명시, 사례 답 없음).

> "리뷰가 한 건만 나온 건 문제가 아니에요. 앞 Human Gate에서 구조를 이미 잡았으니 남은 게 적은
> 거고, reviewer한테 **문제를 억지로 만들지 말라**고 했으니 실제 영향 있는 것만 온 겁니다."

### Human Gate 2 — 반영할 리뷰 선택 (사람)

리뷰를 다 자동 반영하지 않는다. 판정 — 이 문제로 다음 작업자가 사실/해석을 혼동하나 · Codex가 사람
결정 없이 계획을 확정할 수 있나 · 기존 섹션의 질문·완료 판정 한 줄로 풀리나 · 새 섹션·사례 예시 없이
풀리나 · 반영해도 다른 섹션과 중복 안 되나. 리허설의 한 건은 다음 작업자 판단에 영향 + 한 줄로 해결
가능이라 수용:

```
목표: 사람이 승인한 독립 리뷰 항목 하나만 workflow skeleton에 반영한다.
문맥: 현재 @docs/templates/workflow-skeleton.md와 방금 승인한 리뷰 결과를 사용한다.
제약: 현재 파악의 완료 판정에 요청 해석과 확인 전 가설의 구분을 추가하고, 확인된 사실은 근거 또는 현재 동작의 해당 항목으로 연결한다. 현재 동작의 사실을 다시 복사하지 않고 다른 섹션과 다른 파일은 수정하지 않는다.
완료 조건: 승인한 리뷰 문제만 해결됐고 8개 섹션 구조와 빈 템플릿 원칙이 유지된다.
```

> "리뷰·사람의 선택·반영이 이 단계 안에서 끝났어요. 별도 수정 단계를 또 만들지 않습니다."

리뷰가 없었으면 파일을 안 고치고 그대로 통과. 여럿이면 사람이 고른 것만 한 번에 반영한다.

# E3 — Codex Surface 연결과 CLI Handoff 검증 (약 25분)

E1은 진입 문서, E2는 재사용 template. E3는 각 작업을 **어디서 처리할지** 연결한다 — 긴 문맥·사람
판단은 Desktop, 로컬 저장소·명령 검증은 CLI, 실제 웹 화면은 Browser, GUI 조작은 Computer Use,
수동 검증이 끝난 반복은 Scheduled tasks. ⚠️ **네 기능을 억지로 한 번씩 쓰는 게 목적이 아니다.**
작업 특성에 맞는 surface를 고르고, **한 surface의 결과를 다음 surface가 추측 없이 이어받는지**가 핵심.

흐름: 공식 기능 확인 → 작업별 surface 배정 → 사람이 배정 승인 → workflow 문서 반영 → 새 CLI
세션에서 handoff 시험 → 필요한 연결만 보완 → CLI `/review` → 종료 확인.

모델: 기준 조사 Sol · 배정 Sol · 문서 반영 Terra · handoff 시험 Sol(새 CLI 세션·독립) · 보완 Terra ·
`/review` CLI 전용 · 종료 확인 Luna. 이번에 수정하는 파일은 `notes/small-development-workflow.md`
하나 — `docs/templates/`·`src/`·`tests/`는 보존.

## 여는 말 · 시작 상태

`[git status --short / ls notes/small-development-workflow.md docs/templates/workflow-skeleton.md]`

> "작업 트리에 E1·E2 문서가 함께 있을 수 있어요. **기존 변경을 새 변경으로 오인하지 않겠습니다.**
> E3에서 직접 고칠 파일은 `notes/small-development-workflow.md` 하나입니다."

workflow 문서의 `## 현재 멈춘 지점 / ## 바로 다음 작업 / ## 아직 하지 않을 일`도 확인. E1 상태가
그대로 남아 있어도 지금 안 고친다 — **surface 배정이 승인된 뒤 3단계에서 한 번에 최신화한다.**

## 1단계 — Surface 선택 기준 조사 (Sol · $openai-docs)

⚠️ **처음부터 「계획은 Desktop, 검증은 CLI」 답을 주지 않는다.** 각 surface가 뭘 할 수 있고 어떤
작업엔 부적합한지를 **공식 문서로** 먼저 확인한다 — 기능 이름보다 제약을 먼저. 제품 기능은 바뀌니
`$openai-docs`. 이 단계는 repo 파일을 수정하지 않는다.

> "Browser가 있다고 API 검증을 Browser에 넘기거나, 반복 가능성이 확인 안 된 작업을 바로 예약하면
> surface를 잘못 쓰는 거예요. **공식 문서 기준으로 선택 기준부터** 만듭니다."

```
목표: Small Development Workflow에 사용할 Codex surface의 선택 기준을 정리한다.
문맥: $openai-docs를 사용해 Desktop App, Codex CLI, Browser, Computer Use, Scheduled tasks의 현재 공식 역할과 제약을 확인한다.
제약: 아직 repo 파일을 수정하거나 workflow 단계에 surface를 배정하지 않는다. 공식 문서에서 확인되지 않은 기능은 추정하지 않는다.
완료 조건: surface마다 적합한 작업·부적합한 작업·필요한 입력·사람이 정하거나 승인할 것·공식 근거가 표로 정리돼 있다.
```

예상 — 다섯 surface가 「핵심 판단」으로 구분: Desktop(긴 맥락·계획·back-and-forth) / CLI(정확한
저장소에서 파일·명령·종료 코드 반복) / Browser(웹 렌더링 상태 확인) / Computer Use(명령·연동으로
부족해 GUI 직접 조작) / Scheduled(수동 검증 끝난 반복).

검토 — 헤더와 행 열 수 같나 · 근거 링크가 별도 `근거` 열에 있나 · Browser↔Computer Use가 같은
기능처럼 안 쓰였나 · CLI에서 Browser 쓴다고 안 했나 · 수동 검증 전에 Scheduled task 권하지 않았나 ·
Desktop의 위치 선택과 실제 민감 행동 승인이 구분됐나.

리허설 보완점(헤더 5열인데 행은 6열, 설정 선택↔실제 승인 혼재, Browser↔Computer Use 관계 불분명,
전체 CDP 같은 불필요 세부)이 나오면:

```
전체 surface 판단은 승인한다. 다음 부분만 고쳐 표를 다시 보여줘.
- 마지막 근거 링크를 위한 `근거` 열을 추가해 표의 열 수를 맞춘다.
- `사람 확인이 필요한 행동`을 `사람이 정하거나 승인할 것`으로 바꾼다.
- Browser는 웹 화면을 확인하는 작업 공간, Computer Use는 명령이나 구조화된 도구로 충분하지 않을 때 GUI를 조작하는 기능이라는 관계를 드러낸다.
- Browser 행의 `전체 CDP 접근`은 이번 선택 기준에서 제외한다.
아직 repo 파일은 수정하지 마라.
```

공식 기능과 일치하면 다음 단계로. **여기엔 정책 선택이 없으므로 Human Gate를 두지 않는다.**
(참고 문서: Codex CLI / Browser / Computer Use / Scheduled tasks)

## 2단계 — Workflow 작업에 Surface 배정 (Sol)

⚠️ **E2의 8개 섹션을 한 행씩 옮기는 게 아니다.** 같은 맥락·같은 surface를 쓰는 연속 단계를 실제
작업 단위로 **묶는다.** 모든 작업에 다른 surface를 강제 배정하지 않는다. 이 단계도 파일을 수정하지
않고 채팅에서 배정안만.

`[@docs/templates/workflow-skeleton.md @notes/small-development-workflow.md @notes/order-status-plan.md]`
(일반 구조 · 현재 진입점 · 승인된 실행 계획을 함께 — 내용을 다시 합치는 게 아니라 어느 작업이 어느
surface인지 판단)

```
목표: 8단계 workflow를 실제 작업 단위로 묶고 각 작업에 적합한 Codex surface를 배정한다.
문맥: 방금 확인한 surface 선택 기준과 @docs/templates/workflow-skeleton.md, @notes/small-development-workflow.md, @notes/order-status-plan.md를 사용한다.
제약: 아직 파일은 수정하지 않는다. 모든 단계에 다른 surface를 강제로 배정하지 않는다. Browser는 확인할 화면이 있을 때만, Scheduled task는 수동 검증이 안정된 반복 작업의 후보로만 둔다.
완료 조건: 작업 묶음마다 primary surface·입력·산출물 또는 증거·사람 확인 지점·다음 surface로 넘길 handoff가 정리돼 있다.
```

확인할 열 — 작업 묶음(같은 문맥·surface로 묶었나) · Primary surface · 입력(repo 상대 경로) · 산출물/증거 ·
사람 확인 지점(진짜 사람 판단인가) · 다음 handoff(다음 surface가 추측 안 하도록).

리허설 문제(8제목을 그대로 8행, 1~6을 모두 Desktop, 7·8이 E3에서 바로 구현·검증처럼, Browser·
Scheduled 판단 누락, 모든 행에 사람 확인 넣어 자체점검↔Human Gate 혼재)가 나오면:

> "배정표는 나왔는데 실제 업무 단위가 아니라 template 제목을 다시 나열했어요. E3에선 구현 안 하는데
> 구현 단계가 현재 실행처럼 보이고요. 기본 방향은 두고 이 부분만 다시 묶습니다."

```
Desktop과 CLI의 기본 배정 방향은 승인한다.
다음 부분만 고쳐 배정표를 다시 보여줘. 아직 파일은 수정하지 마라.
- 8개 workflow 제목을 한 행씩 옮기지 말고, 같은 맥락과 surface를 사용하는 연속 단계를 작업 단위로 묶는다.
- 구현·테스트 변경과 명령 실행은 E3에서 수행할 작업이 아니라 이후 작업으로 넘길 handoff로 표시한다.
- 현재 API 동작 검증에는 Browser/Computer Use가 필요하지 않음을 명시하고, Browser에는 이후 GitHub Markdown 렌더링·diff·checks 화면 확인 후보를 둔다.
- 수동 검증이 안정적으로 통과하고 반복 필요가 생긴 뒤에만 사용할 Scheduled task 후보를 추가한다. 이번에는 실제 예약을 만들지 않는다.
- 사람 확인과 Codex의 자체 점검을 구분한다. 정책 결정·범위 승인·외부 변경·예약 활성화처럼 사람 판단이 필요한 지점만 남기고, 나머지는 `없음 — 문서 근거로 판정`으로 표시한다.
- 파일명은 가능한 한 repo 기준 상대 경로로 쓴다.
각 작업 묶음에는 primary surface·입력·산출물 또는 증거·사람 확인 지점·다음 handoff를 유지해라.
```

기대 묶음 — 요청·현재 사실·맥락 정리 / 정책 결정·수정·제외 범위 승인 / 검증 계획·구현 handoff 준비 /
향후 CLI 구현·명령 검증 / 이후 Browser 화면 후보 / 이후 Scheduled task 후보.

**Browser/Computer Use 판정** — order-ops는 Express API 중심. 상태·응답 정확성은 테스트·명령으로
판정하므로 구현 검증에 Browser/Computer Use를 쓰지 않는다. Browser 후보엔 실제 화면(렌더된 Markdown,
commit/PR diff, checks 상태)이 있어야 하고, Computer Use는 구조화 접근으로 안 되는 GUI 조작이 있을
때만 — 이번 workflow엔 배정 안 해도 된다. **Scheduled task 판정** — 지금은 안 만든다. 후보 조건:
동일 검증 명령이 수동 통과 / 실행마다 새 정책 판단 불필요 / 반복 필요가 실제로 생김 / 일정·위치·권한을
사람이 승인 / 실패 시 자동 수정 없이 결과만 보고.

### Human Gate — Surface 배정 승인 (사람)

> "surface를 많이 쓰는 게 목표가 아니라, **더 정확히 수행할 위치와 다음으로 넘길 증거가 충분한지**를
> 봅니다."

확인 — 긴 문맥·정책 판단이 Desktop에 남나 · 구현·명령 검증이 향후 CLI handoff로 표시됐나 · 사람
확인↔자체 점검이 구분됐나 · Browser 후보에 실제 화면 있나 · API 정확성 검증을 Browser/Computer Use에
안 맡겼나 · Scheduled 후보가 수동 검증·반복 필요를 전제하나 · 각 surface 출력이 다음 입력으로 충분한가 ·
구현 전 미결 계약이 숨지 않았나. 문제 행만 고치게 하고, 통과하면:

```
이 surface 배정과 handoff 경계를 승인한다.
이제 승인된 내용만 workflow 진입 문서에 반영해줘.
```

## 3단계 — Workflow 문서에 Surface 연결 (Terra)

승인한 배정안을 `notes/small-development-workflow.md`에 반영. **요청·결정·계획 내용을 다시 복사하지
않고 기준 문서로 연결**한다. E2 template과 앱 코드는 수정 안 함.

```
목표: 승인한 surface 배정과 handoff를 현재 workflow 진입 문서에 반영한다.
문맥: 승인된 배정안과 @notes/small-development-workflow.md를 사용한다.
제약: notes/small-development-workflow.md만 수정한다. 요청·결정·계획 내용을 다시 복사하지 않고 기준 문서로 연결한다. 실제 Scheduled task를 만들거나 구현·검증 명령을 실행하지 않는다.
완료 조건: surface 연결에 작업·입력·산출물 또는 증거·사람 확인·handoff가 있고, 현재 멈춘 지점과 다음 작업이 E3 완료 상태로 갱신돼 있다.
```

기존 상태도 최신화 — **`현재 멈춘 지점`**은 두 상태 구분(강의 진행: E2·E3 완료 / 향후 구현: 정확한
CLI handoff 조건 확인 단계). **`바로 다음 작업`**은 두 경로 안 섞기(Chapter 진행: Lab 06 E4 / 제품
구현: 승인된 plan을 입력으로 한 CLI 작업). **`아직 하지 않을 일`** 유지 — src/tests 구현·검증 명령·보류
정책 확정·실제 Scheduled task·요청·결정·계획 중복 금지.

## 4단계 — 새 Codex CLI 세션에서 Handoff 시험 (Sol · 독립)

⚠️ **Desktop Task는 앞 대화를 기억해 자기가 쓴 handoff의 누락을 자연스럽게 메운다.** 그래서 저장소
root에서 **새 CLI 프로세스**를 열고 workflow 진입 문서 하나만 준다. Desktop 통합 터미널을 써도 되지만,
같은 채팅에서 "CLI 입장으로 검토해줘"로 시뮬레이션하는 건 **독립 handoff가 아니다.** (E2 reviewer
subagent·6강 E1 cold-start와 같은 원리 — 만든 맥락 바깥에서.)

`[pwd / ls AGENTS.md package.json / codex]`

> "지금부터 새 CLI 세션입니다. 이전 Desktop 대화는 안 주고 workflow 진입 문서만 넘겨요. CLI가 링크를
> 따라가며 **구현 준비 상태를 판단**할 수 있는지 봅니다."

```
목표: 이 workflow에서 Codex CLI에 배정된 작업을 실행 가능한 수준으로 인계받았는지 검토한다.
문맥: @notes/small-development-workflow.md와 그 문서가 CLI 입력으로 연결한 파일만 읽는다.
제약: 파일을 수정하거나 검증 명령을 실행하지 않는다. Desktop 대화에서 누락된 내용을 추측하지 않는다.
완료 조건: 작업 디렉터리·입력·구현 범위·명령·통과 기준·실패 시 정지 조건·현재 실행 허용 범위·구현 차단 조건을 항목별로 판정한다.
```

리허설 결과 — 대부분 충족됐으나 두 가지: **CLI 시작 작업 디렉터리 누락**, **구현에 필요한 API 세부
계약 누락**(재고 부족 차단의 HTTP 상태·본문 / 재결제 거부의 상태·메시지 / 실패 정보·결제 실패 사유의
필드명·값·생성 규칙). ⚠️ **이건 handoff 실패가 아니라, CLI가 구현 전에 멈춰야 할 조건을 찾아낸 것이다.**

보완할 판정 — 작업 디렉터리 없으면 상대 경로·root AGENTS.md 적용을 보장 못 하므로 입력은 **부분
충족**. `현재 실행 권한`은 sandbox 권한이 아니라 "구현 시작해도 되는지"를 판정하므로 이름을 **`현재
실행 허용 범위`**로. 세부 계약 누락은 단순 누락이 아니라 **`사람 확인 필요 — 구현 시작 차단`**. 실패 시
정지 조건은 두 경우 구분(코드·테스트 결함: 승인 범위 안 수정 후 그 명령부터 재검증 / 미결 정책·API
계약: 수정 없이 멈춰 필요한 결정 보고). 같은 결과면:

```
handoff 검토 방향은 승인한다. 파일은 수정하지 마라.
다음 네 부분만 정정해 표를 다시 보여줘.
- 작업 디렉터리 누락 때문에 상대 경로 해석과 root AGENTS.md 적용을 보장할 수 없으므로 입력 상태를 부분 충족으로 바꾼다.
- `현재 실행 권한`은 `현재 실행 허용 범위`로 바꾼다.
- 구현에 필요한 세부 계약은 단순 누락이 아니라 `사람 확인 필요 — 구현 시작 차단`으로 판정한다.
- 실패 원인이 코드·테스트 결함이면 승인 범위 안에서 수정할 수 있지만, 미결 정책이나 API 계약이 필요하면 수정하지 않고 멈춰 보고하도록 정지 조건을 구분한다.
작업 디렉터리의 보완안은 절대 경로가 아니라
`AGENTS.md와 package.json이 있는 저장소 root`로 제안해라.
```

CLI는 보고만 하고 파일을 수정하지 않는다.

## 5단계 — Desktop에서 Handoff 최소 보완 (Terra)

⚠️ **CLI가 찾은 누락을 CLI가 직접 고치지 않는다.** 진입 문서를 소유한 Desktop Task로 결과를 가져온다.
전체 배정을 다시 쓰지 않고 **누락된 연결만.** (실제 CLI 결과를 붙여 넣는다)

```
목표: CLI handoff 검토에서 확인된 누락만 workflow 진입 문서에 보완한다.
문맥: @notes/small-development-workflow.md와 아래 CLI 검토 결과를 사용한다.
제약: 작업 디렉터리는 `AGENTS.md와 package.json이 있는 저장소 root`로 쓴다. 미결 API 계약은 임의로 결정하지 않고 구현 시작 차단 조건으로 연결한다. 다른 surface 배정, 기준 문서, src/, tests/는 수정하지 않는다.
완료 조건: CLI handoff에 작업 디렉터리·입력·명령·통과 기준·실패 시 정지 조건·구현 차단 조건이 있고 CLI가 추측 없이 시작 여부를 판정할 수 있다.

[CLI 검토 결과]
여기에 실제 결과를 붙인다.
```

수정 후 — 절대 경로 안 들어갔나 · API 계약 답을 Codex가 새로 만들지 않았나 · 구현 차단 조건이 사람
확인으로 연결됐나 · E4 진행↔향후 구현 handoff가 구분됐나 · 다른 문서까지 수정 안 했나.

## 6단계 — Codex CLI `/review`로 독립 Diff 검토

앞의 handoff 시험은 "다음 작업자가 시작할 수 있는가"였다. 이제 `/review`로 Desktop에서 수정한 E3
diff가 안전·일관적인지 검토한다. ⚠️ **`/review`는 스킬이 아니라 Codex CLI 전용 슬래시 명령**이다.
전용 reviewer가 변경을 읽고 문제를 보고하지만 **working tree는 수정하지 않는다.**

> "이번엔 일반 프롬프트가 아니라 CLI 전용 review 기능이에요. 작업 트리에 E1·E2 변경도 있으니 전체
> uncommitted diff를 그대로 검토하지 않고 **파일과 기준을 제한**하겠습니다."

`[/review → 메뉴에서 Custom review instructions 선택]`

```
Review only notes/small-development-workflow.md.
Focus on the E3 Codex surface connection.
- 작업 특성에 따라 surface가 배정됐는지
- CLI handoff에 저장소 root, 입력, 산출물 또는 증거, 통과 기준, 실패 시 정지 조건이 있는지
- Browser에는 실제 확인할 화면이 있고 API 정확성 검증을 대신하지 않는지
- Computer Use는 GUI 조작이 필요한 경우에만 배정됐는지
- Scheduled task 후보에 수동 검증 선행 조건, 반복 조건, 중단 조건, 사람 승인 지점이 있는지
- 실제 Scheduled task를 생성하라는 지시가 없는지
- 현재 멈춘 지점과 다음 작업이 E3 완료 상태에 맞는지
이미 명시된 미결 계약은 임의로 해결하지 말고,
구현 전에 제대로 멈추게 되어 있는지만 확인해라.
실제로 수정할 필요가 있는 finding만 보고해라.
```

Finding 없으면 통과 — 문제를 만들려 리뷰를 반복하지 않는다. 있으면 사람이 판단(다음 작업자가 잘못된
surface에서 시작하게 만드나 · 구현 차단 조건을 놓치게 하나 · 외부 변경·예약을 승인 없이 하게 하나 ·
기존 표 한 행·handoff 조건만 고쳐 해결되나). ⚠️ **승인한 finding만 Desktop Task로 가져와 수정 —
`/review` 결과 전체를 자동 반영하지 않는다.**

# E4 — Chapter 1 Workflow 한 번에 훑기 (약 8분 · 회고)

⚠️ **여기선 새 프롬프트도, 파일 수정도 없다.** Codex를 안 돌린다. 강사가 화면에서 지금까지 만든
문서들을 하나씩 열어 두고 **이야기로 꿰는** 자리다. 표를 읽어 주는 게 아니라, 1강에서 봤던 문제가
이 문서들로 어떻게 사라졌는지를 말로 되짚는다.

## 여는 말 — 되감기

> "자, 여기서 잠깐 손을 멈추고 뒤를 돌아보겠습니다. 우리가 Chapter 1을 시작할 때 화면에 뭐가 있었죠?
> **「결제 실패 상태를 개선해 달라」는 한 줄**이 전부였어요. 코드도 없었고, 뭘 고쳐야 하는지도 몰랐고,
> 심지어 결제가 실패하면 지금 시스템이 뭘 하는지도 몰랐습니다."

> "그런데 지금 폴더를 보세요. `notes/`에 파일이 몇 개고, `AGENTS.md`가 생겼고, `docs/templates/`까지
> 있어요. 한 줄짜리 요청이 **문서 한 세트**가 된 겁니다. 오늘은 이게 어쩌다 이렇게 됐는지가 아니라,
> **이게 왜 필요했는지**를 1강의 실패와 나란히 놓고 정리하겠습니다."

한 줄로 그린 흐름을 화면에 띄운다 — 애매한 요청 → 요청·현재 사실 기록 → 사람 결정·Human Gate →

> "이 화살표 하나하나가 그냥 단계가 아니에요. **매번 「여기서 Codex가 혼자 판단하게 두면 사고가 난다」는
> 지점**마다 우리가 문서나 게이트를 하나씩 끼워 넣은 겁니다. 그걸 지금부터 짚어 볼게요."

## 1강의 네 가지 실패를, 하나씩

⚠️ **표를 통째로 읽지 말고, 한 행씩 「그때 이랬죠 → 그래서 이걸 만들었죠 → 이제 이렇게 달라졌죠」로
풀어 준다.** 이게 이 회고의 핵심 8분이다.

**① 기억이 사라진다.**
> "1강 첫 실습 기억나세요? 앞에서 열심히 설명하고 결정했는데, 새 Task를 열면 Codex가 그걸 하나도
> 모르는 얼굴로 나왔죠. 매번 처음부터 다시 설명했고요. — 그래서 우리는 대화에 기대는 걸 그만뒀습니다.
> 요청은 `order-status-request.md`에, 결정은 `pending-decisions.md`에, 경계는 `task-boundary.md`에
> 적었고, `small-development-workflow.md`가 「어떤 순서로 읽고 지금 어디서 멈춰 있는지」를 안내하게
> 했어요. 이제 새 세션은 기억을 기대하지 않아요. **문서에서 출발합니다.** 이게 6강 E1에서 cold-start로
> 실제로 검증했던 그 지점이에요."

**② 미결 정책을 혼자 정해 버린다.**
> "두 번째 실패. 애매한 부분이 있으면 Codex가 물어보지 않고 그럴듯하게 정해서 진행해 버렸죠. 재결제를
> 허용할지 말지 같은 건 **사람이 정할 일**인데요. — 그래서 사실 확인과 정책 선택을 갈라놨습니다.
> 미결 질문은 `pending-decisions.md`에 상태로 남고, Human Gate와 `AGENTS.md`의 Rules가 **사람 결정이
> 나오기 전엔 그 선택을 못 하도록** 막아요. 이제 Codex는 승인 안 된 선택이 필요하면 밀고 나가지 않고
> **멈춰서 물어봅니다.**"

**③ 다 됐는지 판단할 근거가 없다.**
> "세 번째. 「고쳤습니다」라는 말은 오는데, 그게 진짜 맞는지 확인할 방법이 없었어요. — 그래서 계획에
> **관찰 가능한 것들**을 남겼습니다. 지금 동작이 뭔지 표로, 어디까지가 수정 범위인지 경계로, 어떤
> 시나리오와 어떤 명령이 통과해야 끝인지를요. 이제 완료는 Codex의 설명이 아니라 **관찰 결과와 명령
> 결과**로 판정합니다. 「고쳤다」가 아니라 「이 명령이 이렇게 나왔다」로요."

**④ 대화가 그냥 증발한다.**
> "마지막. 힘들게 한 작업이 그 창을 닫으면 끝이었어요. 다음 요청 때 아무것도 안 남죠. — 그래서 남기는
> 자리를 나눴습니다. 이번 요청에만 쓰는 기록은 `notes/`, 공통 규칙은 `AGENTS.md`, 그리고 **다음 개발
> 요청에서도 다시 쓸 뼈대**는 `docs/templates/workflow-skeleton.md`에. E2에서 만든 그 빈 템플릿이
> 이거예요. 한 번의 작업이 다음 작업의 **자산**이 된 겁니다."

(표는 화면 참고용으로 띄워 두되, 말은 위 네 문단으로.)

## 문서 세트 — 왜 이렇게 쪼갰나

> "여기서 자주 나오는 질문. 「이걸 왜 이렇게 파일을 여러 개로 나눴어요? 하나에 다 쓰면 안 돼요?」 —
> 안 되는 이유가 있어요. **파일 하나가 딱 하나만 책임지게** 해야, 나중에 뭘 고칠 때 어디를 건드릴지가
> 분명해지거든요. 결정이 바뀌면 `pending-decisions.md`만, 규칙이 바뀌면 `AGENTS.md`만 봅니다."

각 파일을 실제로 한 번씩 열어 가리키며:

- `notes/order-status-request.md` — "요청 원문 그대로. 우리가 해석하기 전의 사용자 말."
- `notes/pending-decisions.md` — "물어본 질문과 확정·보류 상태."
- `notes/task-boundary.md` — "Human Gate랑 스스로 멈출 조건."
- `AGENTS.md` — "어느 Task에서나 먹는 읽기·금지·검증·보고 규칙."
- `notes/order-status-plan.md` — "이번 요청의 현재 동작·수정/제외 범위·검증 계획."
- `notes/small-development-workflow.md` — "지금 작업의 진입점, 다음으로 넘길 handoff."
- `docs/templates/workflow-skeleton.md` — "이 과정을 **다른** 요청에서도 다시 쓰는 빈 뼈대."

> "`notes/`는 이번 요청용, `docs/`는 계속 쓸 것 — 이 구분도 그냥 정한 게 아니라 CONVENTIONS에 있는
> 약속이에요. 7강에서 `order-policy.md`로 정책을 **영구 문서**로 올릴 때 이 구분이 다시 나옵니다."
