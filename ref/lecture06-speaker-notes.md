Part 1 · Chapter 1 · 6강 · 실습 · 약 55분 · **슬라이드 없음** — notes 문서와 Codex를 split 화면으로

Chapter 1의 마무리다. 2강 notes · 3강 task-boundary · 4강 AGENTS.md · 5강 order-status-plan을

## 이 노트 쓰는 법

- 5강과 같은 방식이다. 왼쪽에 lab README·notes 문서, 오른쪽에 Codex. `[@파일]`은 mention, `[…]`는
  화면 조작이다. 인용부호 안은 그대로 읽어도 되는 말이다. ⚠️는 놓치면 뒤가 어긋나는 지점.
- 산출물은 `notes/small-development-workflow.md` 하나다. 기존 문서를 합치지 않고 **연결**한다.

# E1 — Chapter 1 문서 세트를 하나의 handoff로 묶기 (약 15~20분)

지금까지 하나의 요청을 여러 문서로 나눠 처리했다 — 요청·초기 사실, 사람이 결정할 질문, Human
Gate·멈춤 조건, repo 규칙, 현재 동작·수정 범위, 검증 계획. **E1은 이걸 다시 합치지 않는다.** 다음
작업자가 하나의 진입 문서에서 필요한 기준 문서를 찾아가게 연결하고, **맥락 없는 새 Task에서 실제로
이어받을 수 있는지** 검증한다.

모델: 문서 감사 Sol · 결정 반영 Terra · 진입 문서 작성 Terra · cold-start 검증 Terra(일부러 약한
모델) · 최종 확인 Luna.

시작 상태: `order-status-plan.md`에 관련 파일·현재 동작·수정/제외 범위·검증 계획이 있고, Human
Gate 정책 결정은 이미 내렸다. `small-development-workflow.md`는 아직 없다. src·tests 무변경.

## 여는 말

> "지금까지 요청 하나를 여러 문서로 나눠 처리했죠. 요청 원문은 `order-status-request.md`, 사람이
> 답할 질문은 `pending-decisions.md`, Human Gate와 멈춤 조건은 `task-boundary.md`, 최종 수정 범위와
> 검증 계획은 `order-status-plan.md`."

> "근데 **문서가 여러 개 있다고 해서 handoff가 되는 건 아니에요.** 다음 사람이 뭘 먼저 읽어야 하는지,
> 서로 다른 내용이 있으면 뭘 기준으로 삼아야 하는지 알아야죠. 오늘은 문서를 합치지 않고, 각 문서의
> 역할과 우선순위를 연결합니다. 마지막엔 **맥락 없는 새 Task에서 진짜 인수인계가 되는지** 확인해요."

## 1. 문서 역할·충돌 감사 (Sol)

먼저 고치지 않는다. 각 문서가 무엇의 기준인지, 오래된 상태나 충돌이 있는지만 조사시킨다.

`[@order-status-request.md @pending-decisions.md @task-boundary.md @order-status-plan.md 연결]`
(AGENTS.md는 자동 로드 — 결과에서 repo 공통 규칙과 요청별 결정이 구분되는지 본다)

```
목표: Chapter 1 산출물을 다음 작업자가 이어받을 수 있는 하나의 문서 세트로 정리하기 전에 역할·중복·충돌을 점검한다.
문맥: @notes/order-status-request.md @notes/pending-decisions.md @notes/task-boundary.md @notes/order-status-plan.md와 자동 적용된 AGENTS.md를 사용한다.
제약: 내용을 합치거나 새 정책을 결정하지 않는다. 각 문서가 무엇의 기준인지, 다른 문서와 겹치거나 상태가 어긋난 부분만 확인하고 파일은 수정하지 않는다.
완료 조건: 문서별 역할·기준 정보·읽는 순서·다른 문서와의 연결과, 다음 작업자를 막을 충돌·누락을 채팅에 제시한다.
```

> "이건 파일 요약이 목적이 아니에요. **각 문서의 역할**을 봅니다 — 요청 원문은 어느 문서가 기준인지,
> 사람 결정은 어디서 추적하는지, 최신 수정 범위는 어느 문서를 따라야 하는지. 그리고 문서마다 만든
> 시간이 다르니까 초기 추정과 최종 계획이 다를 수 있어요. **모든 차이가 오류는 아닙니다** — 정상적인
> 시간 차이랑 진짜 충돌을 갈라야 해요."

## 2. 감사 Human Gate — 정상 시간차 vs 실제 충돌

⚠️ **Codex가 충돌을 찾았다고 다 고치지 않는다. 여기서 강사가 갈라 준다.**

| 실제로 고쳐야 하는 것 (충돌) | 그대로 두는 것 (정상 시간차) |
| --- | --- |
| 이미 결정된 질문이 `pending-decisions`에 미결로 남음 | `order-status-request`의 초기 추정 ≠ 최종 plan |
| `task-boundary` Gate가 통과 여부를 안 보여줌 | plan 안에 초기 조사와 최종 범위가 함께 있음 |
| 결정 결과 ≠ plan의 수정/제외 범위 | `AGENTS.md`에 이 요청의 구체 정책이 없음 |
| 테스트 범위 결정 ≠ 실제 검증 계획 | |

> "요청 문서의 `## 추정`은 요청을 처음 정리할 때의 가설이에요. 최신 plan과 다르다고 덮어쓰지
> 않습니다. **반면** `pending-decisions`가 이미 답한 질문을 계속 미결로 보여주면, 다음 사람을 잘못
> 멈추게 하니까 이건 고쳐야 해요. `task-boundary`는 Gate 질문·금지 조건은 그대로 두고, **통과
> 상태와 결정·계획 링크만** 더합니다."

## 3. 결정 상태와 Human Gate 기록 최신화 (Terra)

⚠️ **진입 문서를 만들기 전에 이걸 먼저 한다.** 감사에서 드러났듯, 이미 사람이 답한 결정이
`pending-decisions.md`엔 아직 미결로, `task-boundary.md` Gate는 승인 전 상태로만 보인다. 이대로
진입 문서를 만들면 **오래된 상태를 그대로 연결**하게 되고, 다음 작업자가 이미 끝난 결정을 다시 묻는다.
그래서 기존 문서의 현재 상태부터 맞춘 뒤 묶는다.

**여기서 새 정책을 결정하지 않는다.** 5강에서 이미 내린 결정을 문서에 반영만 한다. 손대는 파일은
`pending-decisions.md`·`task-boundary.md` **둘뿐** — request·plan·AGENTS·src·tests는 안 건드린다.

### 사람이 정합 수정 범위 승인

감사 결과를 보고 강사가 먼저 확정한다:

> "감사 결과 기준으로 정합 수정 범위를 승인할게요. `pending-decisions.md`는 **삭제 안 합니다** —
> 2강에서 질문을 발견하고 5강에서 답한 과정을 보여주는 **결정 추적 문서**로 씁니다. 기존 질문·선택지는
> 그대로 두고, 실제 선택 결과랑 plan 적용 위치만 더해요."

> "재고 부족 차단이나 관리자 실패 사유처럼 **기존 질문에 없던 E3 추가 결정**은 원래 선택지에 섞지
> 말고 별도 구역으로 뺍니다. 테스트 범위는 현재 plan의 실제 검증 계획과 맞추고요."

> "`task-boundary.md`엔 **정책 답을 다시 안 적습니다.** Gate가 통과됐다는 상태와 결정·계획 문서 링크만
> 더해요."

### 계약

```
목표: Lab 05에서 이미 내린 사람 결정을 Chapter 1 문서 세트에 반영한다.
문맥: @notes/pending-decisions.md @notes/task-boundary.md @notes/order-status-plan.md와 방금 사람이 승인한 정합 수정 범위를 사용한다.
제약: 새로운 결정을 만들지 않는다. pending-decisions.md의 기존 질문·선택지는 보존하고 각 질문의 처리 상태·실제 선택 결과·plan 적용 위치를 기록한다. 기존 선택지에 없던 E3 추가 결정은 별도 구역으로 분리한다. task-boundary.md에는 각 Human Gate의 통과 상태와 결정·계획 문서 링크만 추가하고 기존 질문과 승인 전 금지 조건은 보존한다. 다른 파일은 수정하지 않는다.
완료 조건: 모든 결정 상태가 현재 order-status-plan.md와 일치하고, E3 추가 결정이 기존 질문의 선택 결과와 구분되며, 두 Human Gate가 통과 상태로 표시돼 있다.
```

⚠️ **Codex 도는 동안 — pending과 보류를 구분하라고 짚는다.**

> "이건 정책 결정이 아니라 이미 내린 결정을 상태에 반영하는 작업이에요. 특히 **pending이랑 보류를
> 구분**해야 합니다. pending은 아직 답이 없어서 다음으로 못 가는 상태고, 보류는 사람이 **이번엔 안
> 하기로 결정한** 상태예요. Lab 05 범위가 확정됐으면, 이번 작업을 막는 미결 질문은 없어야 합니다."

### 결과 확인

**pending-decisions.md** — 제목·도입이 현재 역할을 설명하나 (`## 결정 추적` — 사람이 검토한 질문과
처리 상태를 추적) · 기존 질문·선택지 보존됐나 · 질문마다 처리 상태·실제 선택 결과·plan 적용 위치가
있나 · **확정과 이번 작업 보류가 구분됐나** · 실제 선택 결과가 plan과 일치하나 · 관리자 실패 정보의
원래 선택과 **실패 사유 추가**가 분리됐나 · 재고 부족 **생성 전 차단**이 `## E3에서 추가로 확정한 결정`
구역에 있나.

**task-boundary.md** — Gate 1·2에 `통과 상태: 통과` + 결정 문서(pending-decisions)·계획 문서(plan)
링크가 붙었나 · 기존 질문·승인 전 금지 조건 보존됐나 · 결정 내용을 Gate에 다시 복사하지 않았나.

> "Gate가 통과됐다고 승인 전 금지 조건을 지우지 않아요. 이건 지금 다음 작업을 막는 규칙이 아니라,
> **당시 왜 사람이 필요했고 승인 전엔 뭘 하면 안 됐는지 보여주는 작업 이력**이에요. 거기에 통과
> 여부랑 결정 문서 위치만 더하는 겁니다."

### 리허설 피드백 — 테스트 범위가 어긋난 경우

"실제 선택 결과: 완료 조건의 네 흐름만 검증"으로 나올 수 있는데, 현재 plan은 더 넓은 범위를 쓴다.
기존 두 번째 선택지("실패 주문 조회·재고 유지·관리자 조회·재결제·중복 차감 방지 모두")를 plan에 맞게
「관리자 조회」→「관리자 실패 사유 조회」로 명확히 하고 그걸 실제 결과로 삼는다:

```
테스트 범위만 현재 order-status-plan.md와 맞게 고쳐줘.
두 번째 선택지의 "관리자 조회"를 "관리자 실패 사유 조회"로 명확히 바꾸고,
실제 선택 결과는 수정된 두 번째 선택지로 기록해라.
기존 선택지는 이력으로 보존하고, 다른 내용과 파일은 수정하지 마라.
```

수정 후 실제 결과 — 실패 주문 조회 · 재고 유지 · **관리자 실패 사유 조회** · 재결제 · 중복 차감 방지.

### 정합 검증 (Luna)

기록 후 파일은 안 고치고 검토만:

```
방금 수정한 문서 정합을 검토해줘.
pending-decisions.md의 모든 결정 상태와 실제 선택 결과가
order-status-plan.md의 수정·제외 범위와 테스트·검증 계획에 일치하는지 확인해라.
task-boundary.md의 Human Gate 1·2가 통과 상태인지, 기존 질문과 승인 전 금지 조건이 보존됐는지 확인해라.
새 정책이 추가됐거나 요청·계획 내용이 중복 복사됐는지도 확인해라.
문제가 없다면 파일은 수정하지 말고 결과만 보고해줘.
```

변경 범위: `git diff -- notes/pending-decisions.md notes/task-boundary.md` — **두 파일만** 바뀌고
질문·선택지가 보존됐는지, 예상 못한 정책이 안 붙었는지 본다. `git diff --stat -- src/ tests/` 는
출력이 없어야 한다. (order-status-plan.md도 안 바뀌어야 한다.)

## 4. Workflow 진입 문서 만들기 (Terra)

이제 문서 상태가 일치한다. 다음 작업자가 모든 문서를 직접 찾지 않게 `small-development-workflow.md`를
진입점으로 만든다. **상세 내용은 복사하지 않고, 역할·읽는 순서·현재 상태·다음 작업만 연결한다.**

```
목표: 승인한 Chapter 1 문서 관계를 다음 작업자의 진입점인 notes/small-development-workflow.md로 정리한다.
문맥: @notes/order-status-request.md @notes/pending-decisions.md @notes/task-boundary.md @notes/order-status-plan.md와 자동 적용된 AGENTS.md를 사용한다.
제약: 요청·결정·계획의 상세 내용을 복제하지 않고 기준 문서에 연결한다. E2의 재사용 가능한 workflow template과 E3의 Codex surface 배정은 아직 작성하지 않는다. 새 정책을 추가하거나 src/와 tests/를 수정하지 않는다.
완료 조건: 진입 문서에서 현재 작업, 문서 세트와 역할, 읽는 순서, 현재 멈춘 지점, 다음 작업, 아직 하지 않을 일을 찾을 수 있다.
```

기대 구조 — `# Small Development Workflow` 아래: `## 현재 작업` · `## 문서 세트와 역할` · `## 읽는
순서` · `## 현재 멈춘 지점` · `## 다음 작업` · `## 아직 하지 않을 일`.

> "이건 새 계획 문서가 아니에요. 요청은 요청 문서에, 결정은 결정 문서에, 범위·검증은 plan에 그대로
> 둡니다. 이 파일은 **어떤 문서를 어떤 순서로 읽어야 하는지 알려주는 안내판**일 뿐이에요."

확인 — 현재 작업이 한 문단에서 잡히나 · 문서 역할이 구분됐나 · 요청/결정/계획 기준 문서가 명확한가 ·
읽는 순서가 있나 · Gate 통과·구현 미착수가 표시됐나 · 다음 작업이 뭔지 알 수 있나 · E2 template·E3
surface가 미리 안 들어갔나 · 상세가 중복 복사 안 됐나.

## 5. 새 Task에서 cold-start handoff 검증 (Terra · 일부러 약한 모델)

⚠️ **핵심 증거다. 4·5강의 「새 세션 블라인드 검증」이 이제 문서 세트 전체로 확장된다.**

지금 Task는 앞선 대화를 다 안다 — 문서가 부족해도 기억으로 답한다. 그래서 **맥락 없는 새 Task**를
열고 진입 문서 하나만 준다.

`[Codex Desktop에서 새 Task → @notes/small-development-workflow.md만 연결 → 다른 문서는 mention 안 함]`

```
@notes/small-development-workflow.md를 진입점으로 삼아
이 문서가 연결한 작업 자료를 필요한 순서대로 읽어줘.
파일은 수정하지 말고 다음 작업자가 이어받는다는 관점에서
현재 요청, 확인된 현재 동작, 사람의 확정·보류 결정,
수정·제외 범위, 검증 계획, 현재 멈춘 지점,
바로 다음 작업, 지금 하면 안 되는 일을 보고해줘.
문서만으로 확인할 수 없는 내용은 추측하지 말고 누락으로 표시해줘.
```

> "이 Task엔 이전 대화가 없어요. 그러니 요청·결정·계획을 제대로 설명하면 **문서 연결이 실제로
> 작동한 겁니다.** 반대로 이미 결정한 걸 다시 묻거나 바로 구현하려 하면, 진입 문서에 상태나 다음
> 작업이 부족한 거예요."

**성공 판정** — 새 Task가 이걸 회수하면 성공: `payment_failed` 추가·`refunded` 보류 · 실패 응답 402 ·
실패 주문 보존·재결제 불허 · 재고 부족 생성 전 차단 · 관리자 실패 사유 · 여섯 검증 시나리오 · 검증
명령 순서 · Gate 통과 · 구현 미착수 · **응답 메시지·필드 규칙은 추측하면 안 된다는 점**.

## 6. 리허설 피드백 — 다음 작업을 구현으로 오해한 경우

리허설에서 "승인된 수정 범위 안에서 구현 단계로 진행합니다"로 나올 수 있다. 하지만 Lab 06의 바로
다음은 구현이 아니라 **E2 workflow skeleton 작성**이다.

⚠️ **handoff 실패 전체가 아니다.** 요청·결정·계획은 다 이해했고, 진입 문서의 `## 다음 작업` 표현만
모호한 것이다. 전체를 다시 쓰지 말고 그 섹션만 최소 보완한다 (원래 Task로 돌아가서):

```
cold-start handoff 결과에서 바로 다음 작업이 구현으로 잘못 해석됐다.
notes/small-development-workflow.md의 ## 다음 작업만 수정해줘.
바로 다음 작업은 현재 문서 세트에서 공통 구조를 추출해
docs/templates/workflow-skeleton.md를 만드는 E2임을 명확히 해라.
그다음은 Codex surface 연결이며,
order-status-plan.md는 이후 구현의 입력이지만
Chapter 1에서는 구현과 src/, tests/ 변경을 시작하지 않는다고 적어라.
다른 섹션과 파일은 수정하지 마라.
```

## 7. handoff 재확인 + 최종 검증 (Luna)

새 Task에서 진입 문서를 다시 읽게 한다:

```
@notes/small-development-workflow.md를 다시 읽고
현재 바로 다음 작업과 아직 시작하면 안 되는 작업만 보고해줘. 파일은 수정하지 마라.
```

통과: 바로 다음 = 재사용 가능한 workflow skeleton 작성 / 그다음 = Codex surface 연결 / 아직 안 할 것 =
주문 상태 구현과 src·tests 변경.

최종 체크 — pending-decisions에서 질문·최종 결정 추적 가능 · E3 추가 결정이 기존 선택지와 분리 ·
task-boundary Gate 1·2 통과 · `small-development-workflow.md` 존재 · 기준 문서 구분 · 중복 복사 없음 ·
새 Task가 진입 문서 하나로 상태 설명 · 다음 작업을 skeleton 작성으로 인식 · E2/E3 미작성 · src·tests
무변경(`git diff --stat -- src/ tests/` 출력 없음).

## E1 마무리

> "이번 실습에서 문서를 하나로 합치지 않았어요. 요청은 요청 문서에, 결정은 결정 추적 문서에, Gate는
> 경계 문서에, 범위·검증은 plan에 그대로 뒀죠. 대신 `small-development-workflow.md`를 진입점으로 만들어
> **역할과 읽는 순서를 연결**했습니다."

> "그리고 새 Task에 이 문서 하나만 줘서, 이전 대화 없이도 현재 요청·결정·계획·다음 작업을 복원할 수
> 있는지 확인했어요. 그 과정에서 다음 작업을 구현으로 오해하는 것도 잡았는데, 전체를 다시 쓰지 않고
> **원인이 있는 `## 다음 작업` 연결만** 최소 보완했고요."

> "이제 구체적인 작업 세트 하나가 만들어졌습니다. 다음 E2에서는 여기서 **공통 구조를 뽑아**, 다른
> 요청에도 쓸 수 있는 빈 workflow skeleton으로 바꿉니다."
